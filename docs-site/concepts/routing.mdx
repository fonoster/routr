For every new request, such as an `INVITE`, the Connect processor answers two questions: who is calling, and who is being called? The answer determines the **routing type**, and the routing type determines which access checks run and where the call goes.

## How Connect identifies the caller and the callee

Connect looks up the caller from the user and host in the `From` header, and the callee from the user and host in the Request-URI. For each one, it tries these resources in order:

1. A **Number** whose `telUrl` is `tel:` plus the user part.
2. An **Agent** with that username, but only if the Agent belongs to the Domain named by the host. An Agent from another Domain doesn't match.
3. A **Peer** with that username.

If nothing matches, the party is unknown, which Connect treats as the PSTN.

When the request carries an `X-Connect-Token`, Connect builds the caller from the token's claims instead and looks up the callee as the Peer whose `aor` equals the token's `aorLink`.

## The five routing types

Connect picks the routing type from the kinds of the two parties:

| Caller | Callee | Routing type |
| --- | --- | --- |
| Agent | Agent in the same Domain | `agent-to-agent` |
| Agent | Unknown | `agent-to-pstn` |
| Agent | Peer | `agent-to-peer` |
| Any | Number | `from-pstn` |
| Peer | Unknown | `peer-to-pstn` |

A Peer calling an Agent (`peer-to-agent`) isn't supported: Connect answers `500 Server Internal Error`. Any other combination is unknown, and Connect rejects its `INVITE` with `403 Forbidden`.

### agent-to-agent

An Agent calls another Agent in its Domain, for example `1001` dialing `1002` in `sip.local`. Connect asks the Location Service for the callee's registered route and sends the call there. If the callee isn't registered, Connect answers `480 Temporarily Unavailable`.

### agent-to-pstn

An Agent dials a number that isn't an Agent, Peer, or Number in Routr. Connect checks the caller's Domain for an **egress policy** whose `rule`, a regular expression, matches the dialed number. The first match selects a Number, and that Number's Trunk carries the call. Connect sets the `Privacy` header from the Agent's privacy setting and adds `Remote-Party-ID`, `P-Asserted-Identity`, and the Trunk's authentication. If the Domain has no egress policies, or none matches, Connect answers `500 Server Internal Error`.

### from-pstn

A call arrives from a carrier for one of your Numbers. The Number's `aorLink` says where the call goes, for example `sip:1001@sip.local` for an Agent or `sip:conference@sip.local` for a group of Peers. If a Peer has that `aor`, Connect applies the Peer's [load balancing](/concepts/load-balancing) settings. Connect also adds the Number's `extraHeaders` to the request.

A Number can name a `sessionAffinityHeader`. When the incoming call carries that header, Connect passes its value to the Location Service so that calls with the same value reach the same Peer, for example every caller joining the same conference room.

### peer-to-pstn

A Peer, such as Asterisk, dials a number that Routr doesn't know. Because a Peer isn't bound to a Domain, it must say which Number to call from: the request must include an `X-DOD-Number` header with a Number you own, and may include `X-DOD-Privacy`. Connect uses that Number's Trunk. Without the header, Connect answers `400 Bad Request`; with an unknown Number, `404 Not Found`. If the Number has an `extended.accessKeyId`, the request must carry a matching `X-Access-Key-Id` header or it's rejected with `403 Forbidden`.

### agent-to-peer

An Agent calls a Peer directly. This is designed for Agents that present an `X-Connect-Token` whose `aorLink` names the Peer, such as browser clients calling a feature server. Connect applies the Peer's load balancing settings to pick an instance.

### Caller identity on Trunks

Two Trunk settings change the numbers in calls that cross the Trunk:

- `normalizeToE164` rewrites the From, To, and Request-URI users to `+E.164`. On calls from the Trunk, Connect normalizes before routing, so it finds the Number even when the carrier leaves out the `+`. On calls toward the Trunk, it normalizes after routing, so egress policy rules match the number as the caller dialed it.
- `rewriteFromWithNumber` sets the From of calls leaving through the Trunk to the Number the call is placed from: the Number of the matching egress policy for `agent-to-pstn`, or the `X-DOD-Number` for `peer-to-pstn`.

See [Caller identity](/reference/resources/trunks#caller-identity) for the details.

## Access checks

Connect runs access checks on `INVITE` requests, except those authorized by an `X-Connect-Token`, whose signature is verified instead:

- **agent-to-agent, agent-to-pstn, and peer-to-pstn**: the caller must answer a digest challenge with the password from its Credentials. The first `INVITE` gets `401 Unauthorized` with a challenge.
- **from-pstn**: Connect finds the Trunk whose inbound URI matches the Request-URI host and checks that the dialed Number belongs to that Trunk. If the Trunk has an ACL, the request's source address must match one of the ACL's `allow` entries. The source address is the top `Via` header's `received` value, or its host when `received` is absent. If the Trunk has inbound Credentials, the carrier must also pass a digest challenge.

Domains and Peers also accept an ACL reference. In the current Connect processor, the IP check on `INVITE` is enforced for Trunks.

## The X-Call-Direction header

After routing, Connect adds an `X-Call-Direction` header to the request with the routing type as its value, for example `X-Call-Direction: from-pstn`. Downstream systems, such as a media server or a Middleware, can use it to decide how to treat the call.

Connect first removes any `X-Call-Direction` that came from an untrusted source, together with other platform headers, so a caller from the PSTN can't spoof it. See [SIP headers](/reference/sip-headers) for the full list.
