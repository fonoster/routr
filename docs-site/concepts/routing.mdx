For every new request, such as an `INVITE`, the Connect processor answers two questions: who is calling, and who is being called? The answer determines the **routing type**, and the routing type determines which access checks run and where the call goes.

## How Connect identifies the caller and the callee

Connect looks up the caller from the user and host in the `From` header, and the callee from the user and host in the Request-URI. For each one, it tries these resources in order:

1. A **Number** whose `telUrl` is `tel:` plus the user part.
2. An **Agent** with that username, but only if the Agent belongs to the Domain named by the host. An Agent from another Domain doesn't match.
3. A **Peer** with that username.

If nothing matches, the party is unknown, which Connect treats as the PSTN.

A call that arrives on a Trunk is different: when the Request-URI host is a Trunk's `inbound.uri` and the request has no `X-Connect-Token`, the Trunk alone decides the callee, among its own Numbers. See [A Number written another way](#a-number-written-another-way).

### A Number written another way

A carrier doesn't always write a Number the way you stored it. On a call from a Trunk, Connect looks for the callee only among that Trunk's Numbers, in this order:

1. **Exact**: a Number of the Trunk whose `telUrl` is `tel:` plus the user. `+442079460018` finds `tel:+442079460018`. On a Trunk with the deprecated `normalizeToE164`, the user as normalized is also tried here.
2. **Digits**: a Number of the Trunk with the same digits, without the `+`. `442079460018` finds it.
3. **National** or **international**: the user read as a number of the country of each of the Trunk's Numbers, its `countryIsoCode`. For a `GB` Number `tel:+442079460018`, `02079460018` and `2079460018` are national, and `00442079460018` is international. The international form starts with the international prefix of the Number's country: `00` from the UK, `011` from the US, `0011` from Australia. A Number whose `countryIsoCode` isn't a known country is skipped at this step.
4. **Alias**: a Number of the Trunk that lists the user in its [`aliases`](/reference/resources/numbers), compared exactly, case included. This is for a carrier that sends a label, such as `sales` or `01234`, instead of the number.

Each step runs only when the one before finds nothing. A Number with no Trunk, or on another Trunk, never matches, not even exactly. If one step finds two different Numbers of the Trunk, the match is ambiguous: for example `2079460018` on a Trunk with both `tel:+442079460018` (`GB`) and `tel:+12079460018` (`US`). Connect then answers `404` and logs a warning naming both Numbers.

The number Connect reads is the Request-URI user as the carrier sent it, up to its first `;`, so parameters such as `;npdi` are dropped. It never reads the `To` header. The Trunk's ACL and credentials are checked before any lookup, so a carrier gets the same answer whether or not the number exists. There is no partial match: `79460018` doesn't find the Number above unless it is one of its aliases.

A matched call is a `from-pstn` call to that Number. Connect forwards `From` and `To` as it received them, so your application sees the called number as the carrier wrote it, and adds `X-DID-Number` with the Number's `+E.164` to every call it routes, in place of any copy the carrier sent. See [SIP headers](/reference/sip-headers#x-did-number). The step that matched is recorded in the call's trace as `numberMatch`: `exact`, `digits`, `national`, `international` or `alias`.

A new Number answers to its exact form at once. Its other forms and its aliases match as soon as the API Server's lookup cache serves it, which can take up to 360 seconds when the call is served by another API Server instance.

If no Number of the Trunk matches, Connect answers `404 Not Found` with the reason `No Number found for <user>`, the user as it was received.

When the request carries an `X-Connect-Token`, Connect builds the caller from the token's claims instead and looks up the callee as the Peer whose `aor` equals the token's `aorLink`.

## The five routing types

Connect picks the routing type from the kinds of the two parties:

| Caller | Callee | Routing type |
| --- | --- | --- |
| Agent | Agent in the same Domain | `agent-to-agent` |
| Agent | Unknown | `agent-to-pstn` |
| Agent | Peer | `agent-to-peer` |
| Any | Number | `from-pstn` |
| Peer | Unknown | `peer-to-pstn` |

A Peer calling an Agent (`peer-to-agent`) isn't supported: Connect answers `500 Server Internal Error`. Any other combination is unknown, and its `INVITE` gets one of these:

- `401 Unauthorized` when the Request-URI host is a Trunk's and the request comes from outside the Trunk's ACL (no challenge), or lacks the Trunk's credentials (with a challenge).
- `404 Not Found` when the Request-URI host is a Trunk's, the Trunk's ACL and credentials pass, and the user [matches none of the Trunk's Numbers](#a-number-written-another-way).
- `403 Forbidden` in every other case.

An `INVITE` without credentials is challenged with `401 Unauthorized` before Connect looks the caller up (except from a Trunk or with an `X-Connect-Token`), so an unknown caller sees `403` only once it answers the challenge.

### agent-to-agent

An Agent calls another Agent in its Domain, for example `1001` dialing `1002` in `sip.local`. Connect asks the Location Service for the callee's registered route and sends the call there. If the callee isn't registered, Connect answers `480 Temporarily Unavailable`.

### agent-to-pstn

An Agent dials a number that isn't an Agent, Peer, or Number in Routr. Connect checks the caller's Domain for an **egress policy** whose `rule`, a regular expression, matches the dialed number. The first match selects a Number, and that Number's Trunk carries the call. Connect sets the `Privacy` header from the Agent's privacy setting and adds `Remote-Party-ID`, `P-Asserted-Identity`, and the Trunk's authentication. If the Domain has no egress policies, or none matches, Connect answers `500 Server Internal Error`.

### from-pstn

A call arrives from a carrier for one of your Numbers. The Number's `aorLink` says where the call goes, for example `sip:1001@sip.local` for an Agent or `sip:conference@sip.local` for a group of Peers. If a Peer has that `aor`, Connect applies the Peer's [load balancing](/concepts/load-balancing) settings. Connect also adds the Number's `extraHeaders` to the request, and `X-DID-Number` with the Number's `+E.164`; an extra header named `X-DID-Number` is not sent, since Connect's own replaces it.

A Number can name a `sessionAffinityHeader`. When the incoming call carries that header, Connect passes its value to the Location Service so that calls with the same value reach the same Peer, for example every caller joining the same conference room.

### peer-to-pstn

A Peer, such as Asterisk, dials a number that Routr doesn't know. Because a Peer isn't bound to a Domain, it must say which Number to call from: the request must include an `X-DOD-Number` header with a Number you own, and may include `X-DOD-Privacy`. Connect uses that Number's Trunk. Without the header, Connect answers `400 Bad Request`; with an unknown Number, `404 Not Found`. If the Number has an `extended.accessKeyId`, the request must carry a matching `X-Access-Key-Id` header or it's rejected with `403 Forbidden`.

### agent-to-peer

An Agent calls a Peer directly. This is designed for Agents that present an `X-Connect-Token` whose `aorLink` names the Peer, such as browser clients calling a feature server. Connect applies the Peer's load balancing settings to pick an instance.

### Caller identity on Trunks

These Trunk settings change the numbers in calls that cross the Trunk:

- `calledNumberFormat` and `callerNumberFormat` write the called number and the caller's Number the way the carrier requires on calls leaving through the Trunk: `e164`, `e164-without-plus`, `national` or `international`, with an optional prefix. Calls from the Trunk don't need them: the Trunk's Numbers are matched [however the carrier writes them](#a-number-written-another-way).
- `normalizeToE164` (deprecated) rewrites the From, To, and Request-URI users to `+E.164`. On calls toward the Trunk, a format wins over it for the numbers the format covers. Use the formats instead.
- `rewriteFromWithNumber` sets the From of calls leaving through the Trunk to the Number the call is placed from: the Number of the matching egress policy for `agent-to-pstn`, or the `X-DOD-Number` for `peer-to-pstn`. It also sets To's host and port to the Trunk's outbound URI, so To matches the Request-URI.

See [Caller identity](/reference/resources/trunks#caller-identity) and [Number formats](/reference/resources/trunks#number-formats) for the details.

## Access checks

Connect runs access checks on `INVITE` requests, except those authorized by an `X-Connect-Token`, whose signature is verified instead:

- **agent-to-agent, agent-to-peer, peer-to-agent, agent-to-pstn, and peer-to-pstn**: the caller must answer a digest challenge with the password from its Credentials. The first `INVITE` gets `401 Unauthorized` with a challenge. A nonce older than `NONCE_MAX_AGE` seconds (default 300) gets a fresh challenge with `stale=true`.
- **from-pstn**: Connect finds the Trunk whose inbound URI matches the Request-URI host. If the Trunk has an ACL, the request's source address must match one of the ACL's `allow` entries, or it gets `401 Unauthorized` with no challenge. The source address is the top `Via` header's `received` value, or its host when `received` is absent. If the Trunk has inbound Credentials, the carrier must also pass a digest challenge. Both checks run before Connect looks for the Number, which it looks for only among the Trunk's own Numbers: a Number with no Trunk or on another Trunk gets `404 Not Found`.

Domains and Peers also accept an ACL reference. In the current Connect processor, the IP check on `INVITE` is enforced for Trunks.

## The X-Call-Direction header

After routing, Connect adds an `X-Call-Direction` header to the request with the routing type as its value, for example `X-Call-Direction: from-pstn`. Downstream systems, such as a media server or a Middleware, can use it to decide how to treat the call.

Connect first removes any `X-Call-Direction` that came from an untrusted source, together with other platform headers, so a caller from the PSTN can't spoof it. See [SIP headers](/reference/sip-headers) for the full list.
