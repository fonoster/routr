The Connect processor is Routr's built-in Processor. It implements the PBX portion of SIP Connect 1.1 (not certified): it handles registrations and routes calls between Agents, Peers, and the PSTN using the resources stored in the Data API. It is stateless.

Inside RoutrOne, Connect is the `spec.connect` section of `routr.yaml` and reaches the Location and the Data API in process. On its own, it is the `fonoster/routr-connect` image.

## Docker image

`fonoster/routr-connect`

The image reads `/etc/routr/connect.yaml` (`CONFIG_PATH`). Routr 2's Connect had no file and read its settings from the environment; the names are the same, in camelCase under `spec`.

## Ports

| Port | Protocol | Purpose |
| --- | --- | --- |
| `51904` (`spec.bindAddr`) | gRPC | `Processor` service and the standard gRPC health service |

## Configuration

Every key, type and default is in [connect.yaml](/reference/configuration-files#connect-yaml) and [spec.connect](/reference/configuration#spec-connect).

### Service

| Key | Default | Description |
| --- | --- | --- |
| `spec.bindAddr` | `0.0.0.0:51904` | Where it listens |
| `spec.locationAddr` | | Required. Location address, for example `location:51902` |
| `spec.locationAuth` | Plaintext | How to reach it. See [client keys](/reference/configuration#client-keys) |
| `spec.apiAddr` | | Required. Data API address, for example `apiserver:51907` |
| `spec.apiAuth` | Plaintext | How to reach it. The Data API requires authentication beyond loopback, so this usually holds an `apiKey` |
| `spec.registerDefaultExpires` | `3600` | Seconds a registration lasts when the REGISTER carries neither a Contact `expires` parameter nor an `Expires` header. At least `1` |
| `spec.nonceMaxAge` | `300` | Seconds a digest nonce Connect issued stays valid, on INVITE and REGISTER. Credentials that verify against an older nonce get `401` with `stale=true`, and a client retries with the new nonce without asking the user again. `0` accepts any nonce; set it when you replay recorded calls |
| `apiKeys`, `tls`, `insecure` under `spec` | | Who may call it. See [server keys](/reference/configuration#server-keys). Optional: without them it serves anyone and logs a warning |

Connect challenges an `INVITE` that carries no `Authorization` before it looks the caller up, unless the Request-URI host is a Trunk's inbound URI or the request carries an `X-Connect-Token`. A caller Routr doesn't know therefore gets `401 Unauthorized` first and `403 Forbidden` only after it answers the challenge.

A REGISTER whose `To` isn't the authenticated Agent gets `403 Forbidden`.

### Number normalization

Connect normalizes numbers per Trunk, not with a setting. Set `spec.normalizeToE164` on each Trunk that needs it; see [caller identity](/reference/resources/trunks#caller-identity).

### Connect Token verification

These keys verify the JWT in the `X-Connect-Token` header. Set at most one of `verifierAddr` and `verifierPublicKeyPath`; both stop Connect at startup. With neither, a Connect Token is not accepted.

| Key | Description |
| --- | --- |
| `verifierPublicKeyPath` | A PEM public key that verifies tokens in process. Only `RS256` tokens are accepted. `exp` and `nbf` are checked when the token has them; a token without `exp` is accepted with a warning |
| `verifierIssuer` | The `iss` a token verified with `verifierPublicKeyPath` must carry |
| `verifierAudience` | What the `aud` of a token verified with `verifierPublicKeyPath` must name |
| `verifierAddr` | A remote gRPC verifier that implements `fonoster.verifier.Verifier/Verify`. It checks issuer and audience itself |
| `verifierAuth` | How to reach `verifierAddr` |

A verified `X-Connect-Token` is removed before the request is forwarded.

### Header stripping

| Key | Default | Description |
| --- | --- | --- |
| `untrustedHeadersToStrip` | See below | Platform headers removed from untrusted requests. Absent is the default list; `[]` turns stripping off |

Untrusted requests are calls from the PSTN and requests authorized only by a Connect Token. The default list is `X-App-Ref`, `X-Call-Ref`, `X-Call-Direction`, `X-DOD-Number`, `X-DOD-Privacy`, `X-Access-Key-Id`, `X-Is-Api-Originated-Type`, `X-Edgeport-Ref`, `X-Gateway-Auth`, `X-Request-Uri`, and `X-Session-Count`. A request with a verified Connect Token keeps `X-App-Ref`. Requests from authenticated Agents and Peers keep all headers.

### EdgePort trust

When the callee is connected to a different EdgePort, Connect adds a Route header to that EdgePort and an `X-Edgeport-Ref` header. A request carrying `X-Edgeport-Ref` skips routing and access checks, so Connect honors the header only from a trusted peer EdgePort.

| Key | Default | Description |
| --- | --- | --- |
| `spec.trustedEdgePortAddresses` | `[]` (trust none) | IPs or CIDRs of your EdgePorts. Matched against the top Via's `received` value, or its host when `received` is absent |
| `spec.trustedEdgePorts` | `[]` (any ref) | EdgePort refs. When set, the `X-Edgeport-Ref` value must be one of them |

From any other source, Connect removes `X-Edgeport-Ref`, logs a warning, and routes the request normally. A `CANCEL` always follows its INVITE's path and is not affected. These keys exist only in `connect.yaml`.

### Registry trust

The Registry's REGISTER carries a Trunk's credentials in `X-Gateway-Auth`. Connect honors that header only from the Requesters that send it, and it never grants the `X-Edgeport-Ref` bypass.

| Key | Default | Description |
| --- | --- | --- |
| `spec.trustedRegistryAddresses` | `[]` (trust none) | IPs, CIDRs or DNS names of the Requesters |

A DNS name is resolved every 10 seconds. If it stops resolving, Connect keeps its last addresses for 30 seconds and then trusts nothing. **A standalone Connect with a Registry must set this key**, or its Trunks don't register. Inside RoutrOne the key doesn't exist: Connect trusts the Requester's `spec.requester.sipHost`.

## gRPC contract

Connect serves the Processor contract and is a client of the Location and the Data API.

| Service | Method | Request | Response |
| --- | --- | --- | --- |
| `fonoster.routr.processor.v2beta1.Processor` | `ProcessMessage` | `MessageRequest` | `MessageResponse` |

See [processor.proto](https://github.com/fonoster/routr/blob/v3/protos/processor.proto), [location.proto](https://github.com/fonoster/routr/blob/v3/protos/location.proto), and the [Connect protos](https://github.com/fonoster/routr/tree/v3/protos/connect).

## Minimal example

This file runs Connect against a Location and a Data API that asks for an API key, and trusts two EdgePorts on a private network.

```yaml connect.yaml
apiVersion: v2beta1
kind: Connect
spec:
  bindAddr: 0.0.0.0:51904
  locationAddr: location:51902
  apiAddr: apiserver:51907
  apiAuth:
    apiKey: secret://env/ROUTR_API_KEY
  trustedEdgePortAddresses: [10.0.0.10, 10.0.0.11]
  trustedEdgePorts: [edgeport-01, edgeport-02]
  trustedRegistryAddresses: [requester]
```

This command runs Connect with that file.

```bash
docker run -it \
  -v $(pwd)/connect.yaml:/etc/routr/connect.yaml \
  -e ROUTR_API_KEY \
  -p 51904:51904 \
  fonoster/routr-connect
```

## Notes

- With a single EdgePort, leave `trustedEdgePortAddresses` empty. With several, list their addresses, or requests forwarded between EdgePorts go through routing and access checks again instead of reusing the route in the message.
- The ref of a standalone EdgePort is its `HOSTNAME` in Docker and Kubernetes. Use those values in `trustedEdgePorts`.
- In-dialog requests are answered `481` unless they match a dialog the EdgePort proxied and go to one of its targets. Routr 2 forwarded them without that check.
- `Privacy` toward a Trunk follows the caller: `id` for an Agent whose privacy is `PRIVATE`, `none` otherwise, and for a Peer, `X-DOD-Privacy`. The `From` header is not made anonymous.
