RTPRelay is a middleware that drives RTPEngine over the NG protocol. It rewrites the SDP of calls so RTPEngine relays the media, which bridges WebRTC clients and SIP clients, helps clients that cannot exchange media directly, and gives SDES-SRTP to legs reached over TLS, such as a carrier trunk. In Routr 3 it is written in Go.

Inside RoutrOne, RTPRelay is the `spec.rtprelay` section of `routr.yaml`: when it is there, RoutrOne runs the relay in process after Connect. On its own, it is the `fonoster/routr-rtprelay` image, which a Dispatcher calls as a middleware.

## Docker image

`fonoster/routr-rtprelay`

The image reads `/etc/routr/rtprelay.yaml` (`CONFIG_PATH`). Unlike Routr 2's, the file is required: the RTPEngine host has nowhere else to come from.

## Ports

| Port                      | Protocol | Purpose                                                     |
| ------------------------- | -------- | ----------------------------------------------------------- |
| `51903` (`spec.bindAddr`) | gRPC     | `Processor` service, used as a middleware by the Dispatcher |

## Configuration

Every key, type and default is in [rtprelay.yaml](/reference/configuration-files#rtprelay-yaml) and [spec.rtprelay](/reference/configuration#spec-rtprelay). The file rejects unknown keys under `spec`, an unknown profile name, and a profile value that is neither a string nor a list of strings, so a typo fails at startup instead of falling back to a default.

| Key in `rtprelay.yaml`                    | Key in `routr.yaml`       | Default                                       | Description                                                                        |
| ----------------------------------------- | ------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------- |
| `spec.bindAddr`                           |                           | `0.0.0.0:51903`                               | Where it listens. RoutrOne serves no RTPRelay port                                 |
| `spec.rtpengine.host`                     | `spec.rtprelay.host`      |                                               | Required. RTPEngine host or IP                                                     |
| `spec.rtpengine.port`                     | `spec.rtprelay.port`      | `22222` in the file; required in `routr.yaml` | RTPEngine NG control port                                                          |
| `spec.rtpengine.timeoutMs`                | `spec.rtprelay.timeoutMs` | `5000`                                        | How long a command waits for RTPEngine's answer, in milliseconds                   |
| `spec.profiles`                           | `spec.rtprelay.profiles`  |                                               | Changes to the profiles below                                                      |
| `apiKeys`, `tls`, `insecure` under `spec` |                           |                                               | Who may call it. See [server keys](/reference/configuration#server-keys). Optional |

### Profiles

RTPRelay classifies every message by the leg it came from and the leg it goes to: a browser (WebRTC) leg or a phone (SIP over UDP, TCP or TLS) leg. A phone leg reached over TLS gets SDES-SRTP, so the two directions that end on a phone have a secure variant. The classification is fixed; the parameters RTPRelay sends to RTPEngine for each case are the profiles, and these are their defaults.

| Profile                 | When                           | Default                                                                                                                                                                                |
| ----------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `web-to-web`            | Browser to browser             | `ICE: force`, `SDES: [off]`, `flags: [trust-address, replace-origin, replace-session-connection]`                                                                                      |
| `web-to-phone`          | Browser to phone on UDP or TCP | `transport-protocol: RTP/AVP`, `DTLS: off`, `ICE: remove`, `rtcp-mux: [demux]`, `replace: [origin, session-connection]`, `flags: [trust-address, SDES-no]`                             |
| `web-to-secure-phone`   | Browser to phone on TLS        | As `web-to-phone`, with `transport-protocol: RTP/SAVP` and `flags: [trust-address]`                                                                                                    |
| `phone-to-web`          | Phone to browser               | `transport-protocol: UDP/TLS/RTP/SAVPF`, `ICE: force`, `DTLS: passive`, `rtcp-mux: [require]`, `replace: [origin, session-connection]`, `flags: [SDES-no, generate mid, strip-extmap]` |
| `phone-to-phone`        | Phone to phone on UDP or TCP   | `transport-protocol: RTP/AVP`, `rtcp-mux: demux`, `ICE: remove`, `flags: [trust-address, replace-origin, replace-session-connection]`                                                  |
| `phone-to-secure-phone` | Phone to phone on TLS          | As `phone-to-phone`, with `transport-protocol: RTP/SAVP`                                                                                                                               |

A profile in the file is merged over the default of the same name one key at a time: set one key and the rest of the default stays. A list replaces the default list; it is not appended to it, which is how you drop a default flag. This file restricts the SRTP crypto suite offered to a carrier reached over TLS and leaves everything else as shipped.

```yaml rtprelay.yaml
kind: RTPRelay
apiVersion: v2beta1
spec:
  rtpengine:
    host: rtpengine
  profiles:
    phone-to-secure-phone:
      SDES:
        - only-AES_CM_128_HMAC_SHA1_80
```

The result for `phone-to-secure-phone` is `transport-protocol: RTP/SAVP`, `rtcp-mux: demux`, `ICE: remove`, the default `flags`, and the new `SDES`. The keys and values are RTPEngine's own; see the [NG control protocol](https://github.com/sipwise/rtpengine/blob/master/docs/ng_control_protocol.md) for what each one does.

### Routr 2 variables

| Name                                                                | Now                                                                |
| ------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `CONFIG_PATH`                                                       | Unchanged, but the file is now required                            |
| `RTPENGINE_HOST`                                                    | `spec.rtpengine.host`; `spec.rtprelay.host` in `routr.yaml`        |
| `RTPENGINE_PORT`                                                    | `spec.rtpengine.port`; `spec.rtprelay.port`                        |
| `RTPENGINE_TIMEOUT`                                                 | `spec.rtpengine.timeoutMs`; `spec.rtprelay.timeoutMs`              |
| `BIND_ADDR`                                                         | `spec.bindAddr`                                                    |
| `RTPRELAY_CONFIG_PATH` (routr-one)                                  | Removed: the profiles are `spec.rtprelay.profiles` in `routr.yaml` |
| `LOGS_LEVEL`                                                        | `logLevel`                                                         |
| `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | `telemetry.otlpEndpoint`                                           |
| `OTEL_SERVICE_NAME`                                                 | No key. The service name is `rtprelay`                             |
| `OTEL_SDK_DISABLED`                                                 | No key. Leave `telemetry.otlpEndpoint` empty                       |

## gRPC contract

| Service                                      | Method           | Request          | Response          |
| -------------------------------------------- | ---------------- | ---------------- | ----------------- |
| `fonoster.routr.processor.v2beta1.Processor` | `ProcessMessage` | `MessageRequest` | `MessageResponse` |

RTPRelay acts on INVITE and ACK with SDP, `180 Ringing` of a browser-to-phone call (its body is removed), responses with SDP, and BYE. It passes every other message through unchanged. See [processor.proto](https://github.com/fonoster/routr/blob/v3/protos/processor.proto).

## Minimal example

This command runs RTPRelay with the file above.

```bash
docker run -it \
  -v $(pwd)/rtprelay.yaml:/etc/routr/rtprelay.yaml \
  -p 51903:51903 \
  fonoster/routr-rtprelay
```

This Dispatcher fragment registers RTPRelay as a post-processor middleware.

```yaml
spec:
  middlewares:
    - ref: rtprelay-middleware
      addr: rtprelay:51903
      postProcessor: true
```

The same relay inside RoutrOne is one section of `routr.yaml`:

```yaml
spec:
  rtprelay:
    host: rtpengine
    port: 22222
```

## Notes

- A standalone RTPRelay does nothing until you add it to the Dispatcher's `spec.middlewares`.
- On Kubernetes, the `rtprelay.rtpeHost` Helm value is required when `rtprelay.enabled` is `true`, and `rtprelay.profiles` sets the profiles; see [Helm values](/reference/helm-values#rtprelay).
- RTPRelay controls media relaying only. Routr is not a media server, and RTPEngine is a separate service you run.
- A leg that uses TLS gets SDES-SRTP: RTPRelay asks RTPEngine for `RTP/SAVP` toward a trunk or phone reached over TLS and keeps plain RTP, or DTLS-SRTP for browsers, on the other leg. See [Secure the server](/guides/secure-the-server#call-a-carrier-over-tls).
