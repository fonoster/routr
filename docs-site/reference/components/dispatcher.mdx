The Message Dispatcher receives messages from the EdgePort, runs the configured middlewares, and forwards each message to the first Processor whose `matchFunc` returns `true`. It is stateless.

Inside RoutrOne, the Dispatcher is the `spec.dispatcher` section of `routr.yaml`. It hands every message to Connect, then to the RTPRelay when `spec.rtprelay` is set, all in process. On its own, it is the `fonoster/routr-dispatcher` image.

## Docker image

`fonoster/routr-dispatcher`

The image reads `/etc/routr/dispatcher.yaml` (`CONFIG_PATH`).

## Ports

| Port                      | Protocol | Purpose                                                  |
| ------------------------- | -------- | -------------------------------------------------------- |
| `51901` (`spec.bindAddr`) | gRPC     | `Processor` service and the standard gRPC health service |

## Configuration

The file is Routr 2's `dispatcher.yaml`, with authentication added. Every key, type and default is in [dispatcher.yaml](/reference/configuration-files#dispatcher-yaml).

| Key                                       | Description                                                                                                                                                                   |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `spec.bindAddr`                           | Where it listens. `0.0.0.0:51901` by default                                                                                                                                  |
| `spec.processors`                         | Processors, evaluated in order. Each takes `ref`, `addr`, `methods` and `matchFunc`, all required                                                                             |
| `spec.middlewares`                        | Middlewares. Each takes `ref`, `addr` and `postProcessor`                                                                                                                     |
| `spec.backendAuth`                        | How to reach every processor and middleware. See [client keys](/reference/configuration#client-keys)                                                                          |
| `spec.recording`                          | Message recording, one `.jsonl` file per call. See [spec.dispatcher](/reference/configuration#spec-dispatcher) and [Record and replay calls](/guides/record-and-replay-calls) |
| `apiKeys`, `tls`, `insecure` under `spec` | Who may call it. See [server keys](/reference/configuration#server-keys). Optional: without them it serves anyone and logs a warning                                          |

A method in `methods` must be a SIP method the Processor service knows, such as `INVITE` or `MESSAGE`. An unknown name, or a processor without `matchFunc` or `methods`, stops the Dispatcher at startup.

A middleware with `postProcessor: true` runs after the Processor. Without it, or with `false`, it runs before.

`matchFunc` receives the JSON form of the `MessageRequest` protobuf ([sipmessage.proto](https://github.com/fonoster/routr/blob/v3/protos/sipmessage.proto)). These are typical match functions:

```javascript
req => true
req => req.method === "MESSAGE"
req => req.message.from.address.uri.user === "alice"
req => req.message.extensions.find(e => e.name === "User-Agent" && e.value.includes("Zoiper"))
```

### Routr 2 variables

| Name                                                                          | Now                                                                    |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `CONFIG_PATH`                                                                 | Unchanged                                                              |
| `LOGS_LEVEL`                                                                  | `logLevel` at the root of the file: `debug`, `info`, `warn` or `error` |
| `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`           | `telemetry.otlpEndpoint`                                               |
| `OTEL_SERVICE_NAME`                                                           | No key. The service name is `dispatcher`                               |
| `OTEL_SDK_DISABLED`                                                           | No key. Leave `telemetry.otlpEndpoint` empty                           |
| `RECORD_MESSAGES`, `RECORD_MESSAGES_PATH`, `RECORD_MESSAGES_MODE` (routr-one) | `spec.dispatcher.recording` in `routr.yaml`, `spec.recording` here     |

## gRPC contract

The Dispatcher serves the same contract as a Processor, so an EdgePort can talk to either. It is also a client of that contract toward each Processor and middleware.

| Service                                      | Method           | Request          | Response          |
| -------------------------------------------- | ---------------- | ---------------- | ----------------- |
| `fonoster.routr.processor.v2beta1.Processor` | `ProcessMessage` | `MessageRequest` | `MessageResponse` |

See [processor.proto](https://github.com/fonoster/routr/blob/v3/protos/processor.proto).

## Minimal example

This file sends every message to the Connect processor.

```yaml dispatcher.yaml
kind: MessageDispatcher
apiVersion: v2beta1
ref: message-dispatcher
spec:
  bindAddr: 0.0.0.0:51901
  processors:
    - ref: connect-processor
      addr: connect:51904
      matchFunc: req => true
      methods:
        - REGISTER
        - MESSAGE
        - INVITE
        - ACK
        - BYE
        - CANCEL
```

This command runs the Dispatcher with that file.

```bash
docker run -it \
  -v $(pwd)/dispatcher.yaml:/etc/routr/dispatcher.yaml \
  -p 51901:51901 \
  fonoster/routr-dispatcher
```

## Quick test with gRPCurl

You can send a message to the Dispatcher with [gRPCurl](https://github.com/fullstorydev/grpcurl). The services don't expose gRPC reflection, so pass the protos with `-import-path` and `-proto`. The paths below are relative to a clone of the [repository](https://github.com/fonoster/routr) on the `v3` branch.

A `MessageRequest` is a full SIP message in JSON form. This command prints its fields.

```bash
grpcurl \
  -import-path protos \
  -proto processor.proto \
  describe fonoster.routr.processor.v2beta1.MessageRequest
```

This command sends the request in `message.json` and prints the `MessageResponse`. Add `-H 'authorization: Bearer <key>'` when the Dispatcher has `apiKeys`.

```bash
grpcurl -plaintext \
  -import-path protos \
  -proto processor.proto \
  -d @ \
  localhost:51901 \
  fonoster.routr.processor.v2beta1.Processor/ProcessMessage < message.json
```

To send a message taken from a call recording, use [`rctl trace send`](/reference/rctl#rctl-trace-send) instead. It builds the request for you and compares the answer with the recorded one.

## Notes

- You need a separate Dispatcher only with more than one Processor or at least one middleware. Otherwise, point the EdgePort at the Processor directly.
- Order matters. The first Processor whose `matchFunc` returns `true` gets the message, so put catch-all functions last.
