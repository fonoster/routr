The Data API stores the Connect resources (Agents, Domains, Peers, Trunks, Numbers, Credentials, and Access Control Lists) and serves them over gRPC. Routr 2 called it the API Server. It has two backends behind the same contract:

- **`postgres`** stores resources in PostgreSQL, on Routr 2's schema as it is. It supports reads and writes, so you can manage resources with [rctl](/reference/rctl) and the [SDK](/reference/sdk).
- **`files`** loads resources from YAML or JSON files at startup, as Routr 2's simpledata did. It is read-only and suited to tests and small, static setups.

Inside RoutrOne, the Data API is the `spec.data` section of `routr.yaml`. On its own, it is the `fonoster/routr-pgdata` image, which serves either backend.

## Docker image

`fonoster/routr-pgdata`

The image reads `/etc/routr/data.yaml` (`CONFIG_PATH`), a file in the shape of `routr.yaml` of which it uses `logLevel`, `telemetry` and `spec.data`. The `fonoster/routr-simpledata` image is gone: set `backend: files`.

Unlike Routr 2's image, it doesn't run database migrations and doesn't generate certificates. Routr 3 needs no migration of a Routr 2 database. To create a new database, run Routr 2's `fonoster/routr-pgdata-migrations` image (the Helm chart pins `2.32.2`) against it first.

## Ports

| Port | Protocol | Purpose |
| --- | --- | --- |
| `51907` (`spec.data.bindAddr`) | gRPC, TLS with `spec.data.tls` | The Data API, for Routr's components, `rctl` and the SDK, plus the standard gRPC health service |

There is one listener. Routr 2's second port, `51908`, is gone; the Helm chart's Service still offers an `external` port `51908` that reaches the same listener.

## Configuration

Every key, type and default is in [spec.data](/reference/configuration#spec-data).

| Key | Description |
| --- | --- |
| `backend` | Required. `postgres` or `files` |
| `url` | Required with `postgres`. Routr 2's `DATABASE_URL`, unchanged |
| `encryptionKey` | The Cloak key that encrypts the password field of Credentials, `k1.aesgcm256.<key>` |
| `path` | Required with `files`. The directory of resource files |
| `bindAddr` | `0.0.0.0:51907` by default. `""` turns it off inside RoutrOne |
| `apiKeys`, `tls`, `insecure` | Who may call it. See [server keys](/reference/configuration#server-keys) |

### Authentication

The Data API returns decrypted credentials and takes writes. On any address other than loopback it refuses to start unless it authenticates callers: set `apiKeys`, which callers send as `authorization: Bearer <key>`, or `tls.clientCAFile`, which accepts a client certificate signed by that CA. Either is enough. To accept an unauthenticated listener, for example on a private Compose network nobody else reaches, set `insecure: true`.

Add `tls.certFile` and `tls.keyFile` so the key doesn't cross the network in clear. Without `tls` the Data API logs a warning saying so.

### PostgreSQL URL

`url` takes the URL Routr 2 used. Prisma's `?schema=` parameter becomes the Postgres `search_path`, and a URL with no schema uses `public`, as Prisma did. Any other parameter is passed to the Postgres driver.

### Encrypted passwords

With `encryptionKey` set, the Data API encrypts the password field of Credentials before writing it and decrypts it on read, in the same format as Routr 2, so passwords written by either version work in both.

Without it, passwords are stored and read in clear. If the database already holds encrypted passwords, the Data API refuses to start:

```text
spec.data.encryptionKey: is empty, but the database holds encrypted passwords; set the key they were written with
```

### Cache

A standalone Data API reads the database on every call; it has no cache. RoutrOne keeps a cache in front of its in-process `FindBy` lookups: found answers live about 300 seconds, empty ones about 60, and a write through the Data API drops the written row and every kind that embeds it. A row changed directly in PostgreSQL shows up in RoutrOne when its entry expires.

### Routr 2 variables

| Name | Now |
| --- | --- |
| `DATABASE_URL` | `spec.data.url`. Write `url: secret://env/DATABASE_URL` to keep reading the variable |
| `CLOAK_ENCRYPTION_KEY` | `spec.data.encryptionKey` |
| `BIND_ADDR` | `spec.data.bindAddr` |
| `EXTERNAL_SERVER_BIND_ADDR` | Removed: one listener |
| `TLS_ON` | `spec.data.tls` |
| `SERVER_CERT`, `SERVER_KEY` | `spec.data.tls.certFile`, `spec.data.tls.keyFile` |
| `VERIFY_CLIENT_CERT`, `CACERT` | `spec.data.tls.clientCAFile`. A client certificate is now one way in, next to the API key |
| `PATH_TO_CERTS`, `CA_CERT_SUBJECT`, `SERVER_CERT_SUBJECT` | Removed: the image doesn't generate certificates |
| `PATH_TO_RESOURCES` (simpledata) | `spec.data.path` with `backend: files` |
| `LOGS_LEVEL` | `logLevel` |
| `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | `telemetry.otlpEndpoint` |
| `OTEL_SERVICE_NAME` | No key. The service name is `data` |
| `OTEL_SDK_DISABLED` | No key. Leave `telemetry.otlpEndpoint` empty |

## Example: PostgreSQL

This file serves a Routr 2 database with an API key over TLS.

```yaml data.yaml
apiVersion: v3
kind: Routr
spec:
  data:
    backend: postgres
    url: secret://env/DATABASE_URL
    encryptionKey: secret://env/CLOAK_ENCRYPTION_KEY
    apiKeys:
      - secret://env/ROUTR_API_KEY
    tls:
      certFile: /etc/routr/certs/server.crt
      keyFile: /etc/routr/certs/server.key
```

This command runs it.

```bash
docker run -it \
  -v $(pwd)/data.yaml:/etc/routr/data.yaml \
  -v $(pwd)/certs:/etc/routr/certs:ro \
  -e DATABASE_URL="postgresql://postgres:postgres@db:5432/routr?schema=public" \
  -e CLOAK_ENCRYPTION_KEY -e ROUTR_API_KEY \
  -p 51907:51907 \
  fonoster/routr-pgdata
```

## Example: resource files

The `files` backend reads every file in `path`. Each file holds a YAML or JSON list of resources of any kind. By convention, use one file per kind:

| File | Kind |
| --- | --- |
| `agents.yaml` | `Agent` |
| `domains.yaml` | `Domain` |
| `peers.yaml` | `Peer` |
| `trunks.yaml` | `Trunk` |
| `numbers.yaml` | `Number` |
| `credentials.yaml` | `Credentials` |
| `acl.yaml` | `AccessControlList` |

For the fields of each kind, see [Resources](/reference/resources/overview). This file defines one Credentials resource:

```yaml
- apiVersion: v2beta1
  kind: Credentials
  ref: credentials-01
  metadata:
    name: Agent Credentials
  spec:
    credentials:
      username: "1001"
      password: "1234"
```

This file serves a resources directory, on a network where nothing else reaches the port:

```yaml data.yaml
apiVersion: v3
kind: Routr
spec:
  data:
    backend: files
    path: /etc/routr/resources
    insecure: true
```

```bash
docker run -it \
  -v $(pwd)/data.yaml:/etc/routr/data.yaml \
  -v $(pwd)/resources:/etc/routr/resources \
  fonoster/routr-pgdata
```

## gRPC contract

Both backends register one service per resource kind.

| Service | Methods |
| --- | --- |
| `fonoster.routr.connect.agents.v2beta1.Agents` | `Create`, `Update`, `Get`, `Delete`, `List`, `FindBy` |
| `fonoster.routr.connect.domains.v2beta1.Domains` | `Create`, `Update`, `Get`, `Delete`, `List`, `FindBy` |
| `fonoster.routr.connect.peers.v2beta1.Peers` | `Create`, `Update`, `Get`, `Delete`, `List`, `FindBy` |
| `fonoster.routr.connect.trunks.v2beta1.Trunks` | `Create`, `Update`, `Get`, `Delete`, `List`, `FindBy` |
| `fonoster.routr.connect.numbers.v2beta1.Numbers` | `Create`, `Update`, `Get`, `Delete`, `List`, `FindBy` |
| `fonoster.routr.connect.credentials.v2beta1.CredentialsService` | `Create`, `Update`, `Get`, `Delete`, `List` |
| `fonoster.routr.connect.acl.v2beta1.ACLService` | `Create`, `Update`, `Get`, `Delete`, `List` |

`List` takes `page_size` and `page_token` and returns `items` and `next_page_token`. `FindBy` takes `field_name` and `field_value`. The protos are unchanged from Routr 2; see the [Connect protos](https://github.com/fonoster/routr/tree/v3/protos/connect).

Deleting Credentials or an ACL that a Trunk references answers `INVALID_ARGUMENT`. Routr 2 answered OK and left the Trunk without them.

## Quick test with gRPCurl

You can call the Data API directly with [gRPCurl](https://github.com/fullstorydev/grpcurl). The services don't expose gRPC reflection, so pass the protos with `-import-path` and `-proto`. The paths below are relative to a clone of the [repository](https://github.com/fonoster/routr) on the `v3` branch.

This command lists the first ten Agents over TLS with an API key. Replace `-cacert` with `-plaintext` for a Data API without `tls`.

```bash
grpcurl -cacert ca.crt \
  -H "authorization: Bearer $ROUTR_API_KEY" \
  -import-path protos/connect \
  -proto agents.proto \
  -d '{"page_size": 10}' \
  localhost:51907 \
  fonoster.routr.connect.agents.v2beta1.Agents/List
```

This command finds an Agent by username, on either backend.

```bash
grpcurl -cacert ca.crt \
  -H "authorization: Bearer $ROUTR_API_KEY" \
  -import-path protos/connect \
  -proto agents.proto \
  -d '{"field_name": "username", "field_value": "1001"}' \
  localhost:51907 \
  fonoster.routr.connect.agents.v2beta1.Agents/FindBy
```

## Notes

- The `files` backend answers `Get`, `FindBy` and `List`. `Create`, `Update` and `Delete` answer "unimplemented", so `rctl` and the SDK can read its resources but not change them.
- The `files` backend refuses to start if a `ref` contains spaces or if two resources share the same `ref`.
- The `postgres` backend stores the `extended` attribute of each resource as JSON. The `files` backend has no equivalent.
