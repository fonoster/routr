Alterations are small functions that take a `MessageRequest` and return a changed copy. A Processor chains them to prepare a request for its next hop: add Via and Record-Route headers, point the Request-URI at the target, add or remove headers. No alteration mutates its input. An alteration that changes the request deep-copies it first; one with nothing to change returns the original object, so compare by value, not by reference. These return the original when they have nothing to do: `addRouteToNextHop` (the Request-URI host is already the route host), `removeHeaders` (an empty list), `normalizeToE164` (`false`), `rewriteFromWithNumber` (no `rewriteFrom`, or an anonymous From), and `swapIdentityFromRouteSet` (no identity mapping on this EdgePort's Route entry).

Some alterations take the request directly. Others are curried: you call them with a `Route` (or other arguments) first, and they return a function of the request.

The Go SDK, `github.com/fonoster/routr/pkg/processor`, has a twin of every function on this page, and the rule there is the opposite: a Go alteration changes the request in place and returns nothing. The Processor owns the `*MessageRequest` its handler receives, so no copy is needed. A Go alteration that takes a route takes it as an argument after the request, and where the Node.js function throws, the Go one returns an `error` and leaves the request as it was. The sections below describe the Node.js functions; the [summary](#summary) gives each one's Go name and signature, and the behavior is the same unless a section says otherwise.

## Import

`@routr/processor` exports the alterations as `Alterations` and the header helpers as `Extensions`. The built-in Connect processor composes them with `pipe` from `fp-ts`.

```typescript
import { Alterations as A, Extensions as E, MessageRequest } from "@routr/processor"
import { Route, CommonTypes as CT } from "@routr/common"
import { pipe } from "fp-ts/function"
```

In Go, one package holds the alterations, the header helpers and the message types. The route and the SIP types come from the generated packages under `pb/`.

```go
import (
	"github.com/fonoster/routr/pkg/processor"
	"github.com/fonoster/routr/pkg/processor/pb/common"
	"github.com/fonoster/routr/pkg/processor/pb/location"
	"github.com/fonoster/routr/pkg/processor/pb/sipmessage"
)
```

The following function is the chain Connect applies to a request routed to its final target (`mods/connect/src/tailor.ts`).

```typescript
export const tailor = (route: Route, request: MessageRequest): MessageRequest => {
  // The Trunk's caller identity settings, and the Record-Route parameters that
  // remember them for the rest of the dialog
  const { req, recordRouteParameters } = applyTrunkIdentity(route, request)
  return pipe(
    req,
    A.decreaseMaxForwards,
    A.removeAuthorization,
    A.removeSelfRoutes,
    A.removeXEdgePortRef,
    A.fixInvalidContact,
    A.fixRequestURI(route),
    A.addSelfVia(route),
    A.applyXHeaders(route),
    A.addSelfRecordRoute(route, recordRouteParameters),
    A.addRouteToNextHop(route)
  )
}
```

`applyTrunkIdentity` runs `normalizeToE164(!!route.normalizeToE164)` and `rewriteFromWithNumber(route)`, which also moves To to the Trunk's host and port, then `identityRewriteParameters` on the result, so the From and To changes are both recorded.

The `Route` argument is usually the result of a Location Service lookup. Its relevant fields are `user`, `host`, `port`, `transport`, `advertisedHost`, `advertisedPort`, `edgePortRef`, `listeningPoints`, `localnets`, `externalAddrs`, `registeredOn`, and `headers`. A route to a Trunk also carries `normalizeToE164` and `rewriteFrom` (`{ user, host }`), from the Trunk's [caller identity settings](/reference/resources/trunks#caller-identity).

In Go the route is `*location.Route`, the message the Location Service's `FindRoutes` returns, with no wrapper type. Its `Port` and `AdvertisedPort` are strings, which the alterations parse. It has no `headers`, `normalizeToE164` or `rewriteFrom`, which are decisions Connect makes and not Location data, so the alterations that read them take them as arguments: `ApplyXHeaders(req, mods)` takes a `[]processor.HeaderModifier` (`Name`, `Value`, and `Remove` for a header to drop), `RewriteFromWithNumber(req, trunk, from)` takes a `*processor.FromRewrite` (`User`, `Host`; `nil` does nothing), and `NormalizeToE164(req)` has no flag: call it or don't.

The following function is the same chain in Go, without the Trunk identity step.

```go
func tailor(req *processor.MessageRequest, route *location.Route, mods []processor.HeaderModifier) error {
	processor.DecreaseMaxForwards(req)
	processor.RemoveAuthorization(req)
	processor.RemoveSelfRoutes(req)
	processor.RemoveXEdgePortRef(req)
	processor.FixInvalidContact(req)
	processor.FixRequestURI(req, route)
	if err := processor.AddSelfVia(req, route); err != nil {
		return err
	}
	processor.ApplyXHeaders(req, mods)
	if err := processor.AddSelfRecordRoute(req, route, nil); err != nil {
		return err
	}
	processor.AddRouteToNextHop(req, route)
	return nil
}
```

The functions marked `error` are the ones whose Node.js twin can throw. `AddSelfVia`, `AddSelfViaUsingExternalAddrs`, `AddRouteToPeerEdgePort` and `AddSelfRecordRoute` return the errors of `EdgeInterface`, the twin of the `getEdgeInterface` helper: `processor.ErrNoInterface` (the target is outside every localnet and the EdgePort has no external address) and `processor.ErrListeningPointHost` (the listening point is bound to another address), which `errors.Is` tells apart, or an error that names the transport the EdgePort doesn't listen on. `AddSelfViaUsingTheRouteHeaders` returns an error for a Route header without a URI.

## Request-URI

### fixRequestURI

```typescript
fixRequestURI(route: Route): (request: MessageRequest) => MessageRequest
```

Sets the Request-URI host, port, and transport parameter to the route's `host`, `port`, and `transport`. When the route came from a registration (`registeredOn` is set) and has a `user`, it also sets the Request-URI user.

```typescript
const out = A.fixRequestURI(route)(request)
```

## Via

### addSelfVia

```typescript
addSelfVia(route: Route): (request: MessageRequest) => MessageRequest
```

Adds a Via header for this EdgePort at the top of the list, with the `rport` flag. It picks the EdgePort interface that faces the route's target. When the route lives on the same EdgePort as the request, it uses the route's network data; otherwise it uses the request's.

```typescript
const out = A.addSelfVia(route)(request)
```

### addSelfViaUsingTheRouteHeaders

```typescript
addSelfViaUsingTheRouteHeaders(request: MessageRequest): MessageRequest
```

Adds a top Via built from the request's Route headers: the only Route header, or the second one when there are several. The transport defaults to UDP. Returns the request unchanged when it has no Route headers.

```typescript
const out = A.addSelfViaUsingTheRouteHeaders(request)
```

### addSelfViaUsingExternalAddrs

```typescript
addSelfViaUsingExternalAddrs(request: MessageRequest): MessageRequest
```

Experimental. Adds a top Via for the EdgePort interface that faces the Request-URI, taking external addresses into account. Connect uses it for `BYE` and `ACK`.

```typescript
const out = A.addSelfViaUsingExternalAddrs(request)
```

### removeTopVia

```typescript
removeTopVia(request: MessageRequest): MessageRequest
```

Removes the first Via header. Connect uses it on responses before it forwards them.

```typescript
const out = A.removeTopVia(response)
```

## Route

### addRouteToNextHop

```typescript
addRouteToNextHop(route: Route): (request: MessageRequest) => MessageRequest
```

Adds a loose Route header (`lr`) for the route's `host`, `port`, and `transport` at the top of the list. Does nothing when the Request-URI host already equals the route host.

```typescript
const out = A.addRouteToNextHop(route)(request)
```

### addRouteToPeerEdgePort

```typescript
addRouteToPeerEdgePort(route: Route): (request: MessageRequest) => MessageRequest
```

Adds a loose Route header that points to the EdgePort holding the target's connection, using the route's `listeningPoints`, `localnets`, and `externalAddrs`. Use it with `addXEdgePortRef` when the target is connected to another EdgePort. See [EdgePort cooperation](/concepts/edgeport-cooperation).

```typescript
const out = pipe(
  request,
  A.addSelfVia(route),
  A.addSelfRecordRoute(route),
  A.addRouteToPeerEdgePort(route),
  A.addRouteToNextHop(route),
  A.addXEdgePortRef,
  A.decreaseMaxForwards
)
```

### removeSelfRoutes

```typescript
removeSelfRoutes(request: MessageRequest): MessageRequest
```

Removes Route headers that point to this EdgePort: those whose host is one of the EdgePort's local network IPs, external addresses or aliases and whose port is the EdgePort's listening port for that transport.

```typescript
const out = A.removeSelfRoutes(request)
```

The two SDKs differ on a Route header whose transport the EdgePort doesn't listen on. `removeSelfRoutes` throws `NoListeningPointError`. Go's `RemoveSelfRoutes` keeps the header, as Connect does: RFC 3261 section 16.4 removes a Route only when it names this proxy.

## Record-Route

### addSelfRecordRoute

```typescript
addSelfRecordRoute(route: Route, parameters?: Record<string, string>): (request: MessageRequest) => MessageRequest
```

Adds a Record-Route header for this EdgePort so later requests in the dialog pass through it. When the interface the request arrived on differs from the one that faces the target (by host, port, or transport), it adds two Record-Route headers, both with `r2=on`. When given, `parameters` (the identity mapping from `identityRewriteParameters`) goes in the URI user part of every header it adds, as `rfo.<b64>.rfn.<b64>.rco.<b64>.rcn.<b64>` (absent pairs left out), and not as header parameters: a user agent keeps the Record-Route URIs (RFC 3261 section 12.1.2) but may drop their parameters. Without it, the URI has no user part.

```typescript
const out = A.addSelfRecordRoute(route)(request)
```

## Headers

### applyXHeaders

```typescript
applyXHeaders(route: Route): (request: MessageRequest) => MessageRequest
```

Applies the route's `headers` list of header modifiers. Each modifier has a `name`, an optional `value`, and an `action` of `HeaderModifierAction.ADD` or `HeaderModifierAction.REMOVE`. It removes every header named in a `REMOVE` modifier. For each `ADD`, it removes any existing header with that name and adds the new value. Names are matched case-insensitively.

```typescript
route.headers = [
  { name: "X-Room-Id", value: "abc-us-123", action: CT.HeaderModifierAction.ADD },
  { name: "X-Debug", action: CT.HeaderModifierAction.REMOVE }
]
const out = A.applyXHeaders(route)(request)
```

### addXEdgePortRef

```typescript
addXEdgePortRef(request: MessageRequest): MessageRequest
```

Adds an `X-Edgeport-Ref` header with the request's `edgePortRef` at the top of the extension headers. The receiving EdgePort uses it to tell the request came from a peer EdgePort. See [SIP headers](/reference/sip-headers).

```typescript
const out = A.addXEdgePortRef(request)
```

### removeXEdgePortRef

```typescript
removeXEdgePortRef(request: MessageRequest): MessageRequest
```

Removes every `X-Edgeport-Ref` header, matched case-insensitively.

```typescript
const out = A.removeXEdgePortRef(request)
```

### removeHeaders

```typescript
removeHeaders(names: string[]): (request: MessageRequest) => MessageRequest
```

Removes every extension header whose name is in `names`, matched case-insensitively. Returns the request unchanged when `names` is empty.

```typescript
const out = A.removeHeaders(["X-Call-Direction", "X-DOD-Number"])(request)
```

### removeAuthorization

```typescript
removeAuthorization(request: MessageRequest): MessageRequest
```

Deletes the Authorization header, so the caller's credentials aren't forwarded.

```typescript
const out = A.removeAuthorization(request)
```

### decreaseMaxForwards

```typescript
decreaseMaxForwards(request: MessageRequest): MessageRequest
```

Subtracts one from Max-Forwards, when the header is present.

```typescript
const out = A.decreaseMaxForwards(request)
```

## Contact

### fixInvalidContact

```typescript
fixInvalidContact(request: MessageRequest): MessageRequest
```

When the Contact host contains `.invalid`, as WebRTC clients often send, replaces it with the top Via's `received` value (or host), the `rport` value (or port), and the Via transport.

```typescript
const out = A.fixInvalidContact(request)
```

### overwriteContactWithSenderInfo

```typescript
overwriteContactWithSenderInfo(request: MessageRequest): MessageRequest
```

Sets the Contact host, port, and transport to the request's `sender` values, when a Contact header is present. Connect does not apply it by default.

```typescript
const out = A.overwriteContactWithSenderInfo(request)
```

## Numbers

### normalizeToE164

```typescript
normalizeToE164(normalize: boolean): (request: MessageRequest) => MessageRequest
```

When `normalize` is `true`, tries to rewrite the From, To, and Request-URI users as E.164 numbers (with a leading `+`). It replaces a value only when it parses as a valid number, landlines included: mobile prefixes are not checked. Returns the request unchanged when `normalize` is `false`. Connect applies it for Trunks with `normalizeToE164`: before routing on calls from the Trunk, and in the tailor on calls toward it.

```typescript
const out = A.normalizeToE164(true)(request)
```

### rewriteFromWithNumber

```typescript
rewriteFromWithNumber(route: Route): (request: MessageRequest) => MessageRequest
```

When `route.rewriteFrom` is set, sets the From URI user and host to `route.rewriteFrom.user` and `route.rewriteFrom.host`, adds `user=phone`, and drops the port. The display name and tag stay. An anonymous From (user `anonymous` or host `anonymous.invalid`) is never rewritten. It also sets the To URI host and port to `route.host` and `route.port`, the Trunk's outbound URI, so To matches the Request-URI; To's user, tag and display name stay, no transport parameter is added, and this happens for an anonymous From too. Returns the request unchanged when `route.rewriteFrom` is not set.

```typescript
const out = A.rewriteFromWithNumber({ ...route, rewriteFrom: { user: "+18295863314", host: "sip.provider.net" } })(request)
```

### identityRewriteParameters

```typescript
identityRewriteParameters(original: MessageRequest, altered: MessageRequest): Record<string, string>
```

Compares the From and To URIs of a request before and after the identity alterations and returns the identity mapping for what changed: `rfo` and `rfn` hold the original and new From, `rco` and `rcn` the original and new To, each as base64url of `user@host[:port][;user=...]` (the port when the URI names one, `;user=` when set). A change of user, host, port or `user=` counts. Returns `{}` when nothing changed. Pass the result to `addSelfRecordRoute`, which writes it in the user part of its Record-Route URI.

In Go, `original` must be a `proto.Clone` of the request, taken before the identity alterations run. They change the request in place, so passing the same request twice returns an empty map. Then `AddSelfRecordRoute` writes no identity, and the dialog's BYE can't be restored (RFC 3261 section 12.1.2).

```go
original := proto.Clone(req).(*processor.MessageRequest)
processor.RewriteFromWithNumber(req, trunk, &processor.FromRewrite{User: "+18295863314", Host: "sip.provider.net"})
params := processor.IdentityRewriteParameters(original, req)
if err := processor.AddSelfRecordRoute(req, trunk, params); err != nil {
	return err
}
```

### swapIdentityFromRouteSet

```typescript
swapIdentityFromRouteSet(request: MessageRequest): MessageRequest
```

For an in-dialog request whose Route entry for this EdgePort carries the mapping above, swaps From and To so each side sees the identities it knows: a request from the caller gets the From and To the Trunk saw, and a request from the Trunk gets the caller's own identity back. It reads only Route entries that point at this EdgePort, so with two EdgePorts on the path only the one that rewrote the INVITE swaps.

It reads the mapping from this EdgePort's Route entry in one of two forms. First the URI user part, `rfo.<b64>.rfn.<b64>.rco.<b64>.rcn.<b64>` (each pair optional, in that order), which a user agent keeps because RFC 3261 section 12.1.2 builds the route set from Record-Route URIs. Each value there is base64url of `user@host[:port][;user=...]`, and it is applied exactly: the URI port is set to the value's port, or to none when the value has no port. When the user part isn't of that form, it reads header parameters of the same names, the form Routr wrote before the mapping moved into the URI, and applies only user, host and `user=`, leaving the port alone. An entry with both forms is swapped once, from the user part.

Run it before `removeSelfRoutes`.

### isAnonymous

```typescript
isAnonymous(uri: CommonTypes.SipURI): boolean
```

Returns `true` when the URI is the anonymous identity of RFC 3323: user `anonymous` or host `anonymous.invalid`, case-insensitively. `rewriteFromWithNumber` uses it to leave a private caller's From alone.

```typescript
const hidden = A.isAnonymous(request.message.from.address.uri)
```

## Header helpers (Extensions)

`Extensions` holds helpers that read and change extension headers. Unlike alterations, they take the header data as a second argument. `getHeaderValue` matches names case-insensitively; the others match the exact name.

| Function | Signature | Go (`processor.`) | Description |
| --- | --- | --- | --- |
| `getHeaderValue` | `(request, name: string) => string \| null` | `HeaderValue(req, name) string` (renamed) | Returns the first header value with that name, or `null`; `""` in Go. |
| `addHeader` | `(request, header: { name, value }) => request` | `AddHeader(req, h)` | Appends a header. |
| `updateHeader` | `(request, header: { name, value }) => request` | `UpdateHeader(req, h)` | Replaces the value of headers with that name. |
| `removeHeader` | `(request, name: string) => request` | `RemoveHeader(req, name)` | Removes headers with that name. |

In Go, `h` is a `processor.Header` (`Name`, `Value`), and the three that change the request change it in place.

The following snippet reads a header and adds another.

```typescript
const roomId = E.getHeaderValue(request, "X-Room-Id")
const out = E.addHeader(request, { name: "X-Room", value: roomId ?? "lobby" })
```

## Go names

Most Go functions are the Node.js name with a capital first letter. The following ones are renamed or take different arguments.

| Node.js | Go | What changed |
| --- | --- | --- |
| `Target.getAOR` | `AOR(uri)` | No `get`. |
| `Target.getTargetAOR`, `Target.getTargetExpires` | `TargetAOR(req)`, `TargetExpires(req, def)` | No `get`. The default is always given; `DefaultExpires` is the Node.js default, 3600. |
| `Extensions.getHeaderValue` | `HeaderValue(req, name)` | No `get`. Returns `""`, not `null`, when the header is absent. |
| `Helper.isOk`, `Helper.isOkOrRingingWithSDP` | `IsOK(req)`, `IsOKOrRingingWithSDP(req)` | `OK` in capitals. |
| `Helper.getEdgeInterface` | `EdgeInterface(nets, endpointHost, transport)` | No `get`. Takes the networks as a `Nets` value, from `NetsOf(req)` or `NetsOfRoute(route)`, and returns an `error`. |
| `normalizeToE164(flag)` | `NormalizeToE164(req)` | No flag. |
| `applyXHeaders(route)` | `ApplyXHeaders(req, mods)` | The modifiers are an argument. |
| `rewriteFromWithNumber(route)` | `RewriteFromWithNumber(req, trunk, from)` | The rewrite is an argument. |
| `removeHeaders(names)` | `RemoveHeaders(req, names...)` | The names are variadic. |
