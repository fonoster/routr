The `routr/routr-connect` chart deploys EdgePort, Message Dispatcher, Connect processor, Location Service, the Data API (`apiserver`), Registry, Requester, and optionally RTPRelay. It can also deploy PostgreSQL and Redis from the Bitnami charts.

From chart 0.5, the chart runs Routr 3. It writes each component's [configuration file](/reference/configuration-files) from these values into a ConfigMap, and passes secrets as `secret://k8s/<secret>#<key>` references to Secrets mounted at `/var/run/routr/secrets/<secret>`. To upgrade from chart 0.4.x, see [Upgrade from Routr 2](/guides/upgrade-to-routr-3#upgrade-the-helm-chart).

| Chart           | Version | App version                              |
| --------------- | ------- | ---------------------------------------- |
| `routr-connect` | `0.5.0` | Set to the Routr version by each release |

Image tags default to the chart's app version.

## Install

These commands add the chart repository and install a release named `routr` in the `routr` namespace.

```bash
helm repo add routr https://routr.io/charts
helm repo update
kubectl create namespace routr
helm install routr routr/routr-connect --namespace routr
```

This command overrides values from a file.

```bash
helm install routr routr/routr-connect --namespace routr -f values.yaml
```

| Key (under the section)            | Type    | Default                  | Description                                                                                                               |
| ---------------------------------- | ------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `replicas`                         | integer | `2`                      | Pods of the Deployment when `autoscaling.enabled` is `false`. `location` above `1` needs `location.cache.provider: redis` |
| `topologySpread.maxSkew`           | integer | `1`                      | Most pods one node may hold above another. `topologySpread: {}` turns the spread off                                      |
| `topologySpread.topologyKey`       | string  | `kubernetes.io/hostname` | What the pods spread over                                                                                                 |
| `topologySpread.whenUnsatisfiable` | string  | `ScheduleAnyway`         | `DoNotSchedule` leaves a pod Pending rather than skew                                                                     |
| `pdb.enabled`                      | boolean | `true`                   | A PodDisruptionBudget, rendered with more than one replica or the autoscaler                                              |
| `pdb.minAvailable`                 | integer | `1`                      | Pods kept through a node drain                                                                                            |

| `dispatcher` | `{"cpu": "250m", "memory": "64Mi"}`  |

## networkPolicy

| Key                         | Type    | Default | Description                                                                                                                                                                                                                                                                                    |
| --------------------------- | ------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `networkPolicy.enabled`     | boolean | `true`  | One NetworkPolicy per internal gRPC service (`location`, `connect`, `dispatcher`, `requester`, `rtprelay`): only this release's pods, plus `ingressFrom`, reach them. The Data API gets none: it authenticates callers. On a CNI that doesn't enforce NetworkPolicy these objects do nothing   |
| `networkPolicy.ingressFrom` | array   | `[]`    | Extra peers admitted to the internal services, as NetworkPolicy `from` entries: an EdgePort, a Dispatcher or a processor outside this release. Another release of this chart named in `dispatcher.processors[].servicePrefix` counts as outside: list this release in that one's `ingressFrom` |

To admit every pod of the namespace `sip-edge`:

```yaml
networkPolicy:
  ingressFrom:
    - namespaceSelector:
        matchLabels: { kubernetes.io/metadata.name: sip-edge }
```

## Securing the Data API

The Data API and the Requester refuse to start without authentication. The chart keeps one API key in the Secret `<release>-routr-api-key` and gives it to the Data API, the Requester, Connect and the Registry. A new install or an upgrade generates it once. Rotating it means setting `apiserver.apiKey`, which rolls those pods; a call between them may fail until they all restart. The pods carry a hash of a key set in values, so it must be random (the chart generates 48 random characters), or use `apiserver.apiKeySecret`.

To keep the key in a Secret of your own, set `apiserver.apiKeySecret` to its name; it holds the key under `apiKey`. Rotating it means editing that Secret and then restarting the apiserver, requester, connect and registry Deployments, which read the key at start. The generated Secret is kept, so you can move back to it by unsetting the value; it also stays after `helm uninstall`, until you delete it.

The Helm `lookup` that keeps the generated key and certificate needs access to the cluster. Something that renders the chart without it, such as a GitOps controller or `helm template`, gets a new key and certificate each time: set `apiserver.apiKeySecret` or `apiserver.apiKey`, and `apiserver.tlsSecret`.

`rctl` and the SDK reach the Data API with the key and the CA, as the install's notes show. Anything else you wrote against `51907` or `51908` must now send `authorization: Bearer <key>`, and speak TLS with `tlsOn`. The Requester takes the key over plaintext inside the cluster (`requesterAuth.insecure: true`); no Service publishes it outside. With [`networkPolicy.enabled`](#networkpolicy), the default, a NetworkPolicy admits only the release's pods to it and to Location, Connect, the Dispatcher and the RTPRelay, which authenticate nobody. It protects only on a CNI that enforces NetworkPolicy.

## Notes

- Bitnami moved its versioned images off `docker.io/bitnami`, so the chart points PostgreSQL and Redis at the `bitnamilegacy` copies. To use your own mirror, override the `image.repository` values above.
- User agents that run inside the cluster need `edgeport.podCIDR`; phones and carriers outside it need `edgeport.externalAddrs`. Don't set `podCIDR` when phones outside the cluster use private addresses in the pod range.
- `connect.trustedEdgePortAddresses` names the release's own EdgePorts by default, so requests forwarded between them skip routing and access checks. An EdgePort outside the release needs its address or name added. See [EdgePort cooperation](/concepts/edgeport-cooperation).
- A release name YAML reads as a boolean or a number (`n`, `on`, `123`) needs `postgresql.enabled` and `redis.enabled` set to `false`: the Bitnami subcharts write it unquoted into their labels.
- The Requester's and the RTPRelay's HorizontalPodAutoscalers are off unless their `autoscaling.enabled` is `true` (`requester.autoscaling.enabled`, `rtprelay.autoscaling.enabled`); their `replicas` (default `1`) set the pods otherwise.
- Liveness probes only: no pod has a readiness probe.
