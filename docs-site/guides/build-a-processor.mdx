Build a gRPC Processor that handles SIP `MESSAGE` requests (instant messaging), then register it in the Message Dispatcher next to the Connect processor.

A Processor receives every SIP message as a protobuf `MessageRequest`, decides where it goes, and returns the modified message. It is the last stop before EdgePort sends the message out. Use one when the built-in [Connect processor](/reference/components/connect) doesn't fit, for example to build an IM service, SCAIP logic, or an IoT integration.

## Prerequisites

- Node.js 22 or later, or Go 1.26 or later, for the language you write the Processor in.
- A running Routr core: an EdgePort, a Message Dispatcher, and a Location Service. Running [Routr from source](/guides/run-from-source) gives you all three.
- Familiarity with the [message flow](/concepts/message-flow).

<Tip>
  The finished example lives in the [nodejs-processor](https://github.com/fonoster/nodejs-processor) template. Run `npx degit fonoster/nodejs-processor my-processor` to start from it instead of from scratch. In Go, the smallest Processor is the [echo example](https://github.com/fonoster/routr/tree/main/pkg/processor/examples/echo) of the SDK, which answers every message with `200 OK`.
</Tip>

## The processor contract

Every Processor implements one RPC, defined in [`processor.proto`](https://github.com/fonoster/routr/blob/main/mods/common/src/protos/processor.proto):

```protobuf
service Processor {
  rpc ProcessMessage (MessageRequest) returns (MessageResponse) {}
}

message MessageRequest {
  string ref = 1;                 // Same as the Call-ID
  string edge_port_ref = 2;       // EdgePort that received the message
  Method method = 3;
  NetInterface sender = 4;
  repeated NetInterface listening_points = 5;
  repeated string external_addrs = 6;
  repeated string localnets = 7;
  fonoster.routr.sipmessage.v2beta1.SIPMessage message = 8;
  map<string, string> metadata = 9;
  string edge_port_version = 10;  // Version of the EdgePort, for example 2.18.0
  NetInterface received_on = 11;  // Local socket the message arrived on
  repeated string aliases = 12;   // Hostnames the EdgePort answers to
}

message MessageResponse {
  NetInterface sender = 1;
  fonoster.routr.sipmessage.v2beta1.SIPMessage message = 2;
  map<string, string> metadata = 3;
}
```

The request carries everything the Processor needs (sender, listening points, networks), so a Processor holds no state and scales horizontally. You can write one in any language with gRPC support. In Node.js, `@routr/processor` hands you the request as JSON. In Go, `github.com/fonoster/routr/pkg/processor` hands you the same message as a `*processor.MessageRequest`, read with its getters (`req.GetMethod()`, `req.GetMessage().GetFrom()`). This excerpt shows the shape of a `REGISTER`:

## Build the IM processor

<Steps>
  <Step title="Create the project">
    <Tabs>
      <Tab title="Node.js">
        Create a folder and install the Processor library, the Location Service client, and `fp-ts` for `pipe`:

        ```bash
        mkdir im-processor && cd im-processor
        npm init -y
        npm install --save @routr/processor @routr/location fp-ts
        ```
      </Tab>
      <Tab title="Go">
        Create a folder and a module, and add the Processor SDK. The SDK is its own Go module, and it includes the Location Service client:

        ```bash
        mkdir im-processor && cd im-processor
        go mod init im-processor
        go get github.com/fonoster/routr/pkg/processor@latest
        ```
      </Tab>
    </Tabs>
  </Step>

  <Step title="Start the gRPC server">
    <Tabs>
      <Tab title="Node.js">
        Create `index.js`. It connects to the Location Service and starts a Processor on port `51904` that sends `REGISTER` and `MESSAGE` to handlers and rejects everything else:

        ```javascript index.js
        const Processor = require("@routr/processor").default
        const { LocationClient } = require("@routr/location")
        const { createHandlers } = require("./handlers")

        const locationClient = new LocationClient({ addr: "localhost:51902" })
        const handlers = createHandlers(locationClient)

        new Processor({ bindAddr: "0.0.0.0:51904", name: "instant-messaging" })
          .listen(async (req, res) => {
            try {
              const method = req.method.toString()
              if (method === "REGISTER") await handlers.register(req, res)
              else if (method === "MESSAGE") await handlers.sendMessage(req, res)
              else res.sendNotImplemented()
            } catch (error) {
              console.error("An error occurred:", error)
              res.sendInternalServerError()
            }
          })
        ```
      </Tab>
      <Tab title="Go">
        Create `main.go`. It connects to the Location Service and starts a Processor on port `51904` that sends `REGISTER` and `MESSAGE` to handlers and rejects everything else:

        ```go main.go
        package main

        import (
        	"context"
        	"log"
        	"os"
        	"os/signal"
        	"syscall"

        	"github.com/fonoster/routr/pkg/processor"
        	"github.com/fonoster/routr/pkg/processor/pb/location"
        	"google.golang.org/grpc"
        	"google.golang.org/grpc/credentials/insecure"
        )

        func main() {
        	conn, err := grpc.NewClient("localhost:51902", grpc.WithTransportCredentials(insecure.NewCredentials()))
        	if err != nil {
        		log.Fatal(err)
        	}
        	defer conn.Close()
        	h := &handlers{location: location.NewLocationClient(conn)}

        	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
        	defer stop()
        	err = processor.ListenAndServe(ctx, processor.Options{BindAddr: "0.0.0.0:51904", Name: "instant-messaging"},
        		func(ctx context.Context, req *processor.MessageRequest) (*processor.MessageResponse, error) {
        			switch req.GetMethod() {
        			case processor.Method_REGISTER:
        				return h.register(ctx, req)
        			case processor.Method_MESSAGE:
        				return h.sendMessage(ctx, req)
        			default:
        				return processor.NotImplemented(), nil
        			}
        		})
        	if err != nil {
        		log.Fatal(err)
        	}
        }
        ```

        `ListenAndServe` runs until `ctx` is done, then stops gracefully.
      </Tab>
    </Tabs>

    The SDK calls your function once per message. In Node.js it gets the `MessageRequest` and a `Response`, and you answer every call with one of the `Response` methods. In Go it gets a `context.Context` and the `*processor.MessageRequest`, and you answer by returning what one of the response functions builds:

    | Node.js (`res.`) | Go (`processor.`) | Result |
    | --- | --- | --- |
    | `send(request)` | `Forward(req)` | Returns the (altered) message to EdgePort, which forwards it |
    | `sendOk(extraHeaders?)` | `OK(extra...)` | Replies `200 OK` |
    | `sendRegisterOk(request, extraHeaders?, metadata?)` | `RegisterOK(req, metadata, extra...)` | Replies `200 OK` with the request's Contact. `metadata` goes back to the Message Dispatcher, for example the recording flag |
    | `sendNotFound()` | `NotFound()` | Replies `404 Not Found` |
    | `sendForbidden(message?)` | `Forbidden(reason)` | Replies `403 Forbidden` |
    | `sendMethodNotAllowed()` | `MethodNotAllowed()` | Replies `405 Method Not Allowed` |
    | `sendTemporarilyUnavailable()` | `TemporarilyUnavailable()` | Replies `480 Temporarily Unavailable` |
    | `sendNotImplemented()` | `NotImplemented()` | Replies `501 Not Implemented` |
    | `sendInternalServerError()` | `InternalServerError()` | Replies `500 Internal Server Error` |
    | `sendBadGateway(reasonPhrase?)` | `BadGateway(reason)` | Replies `502 Bad Gateway`, for a next hop that can't be reached as configured |
    | `sendError(error)` | Return an `error` | Deprecated. Fails the gRPC call with `error` instead of replying with a SIP response |

    In Go, `Forbidden("")` and `BadGateway("")` use the default reason phrase, and an extra header is a `processor.Header{Name, Value}`.
  </Step>

  <Step title="Handle REGISTER">
    <Tabs>
      <Tab title="Node.js">
        Create `handlers.js`. The `register` handler stores the sender's route in the Location Service under the target AOR and replies `200 OK` with the request's Contact:

        ```javascript handlers.js
        const { Alterations, Target, Helper: ProcessorHelper } = require("@routr/processor")
        const { Helper: LocationHelper } = require("@routr/location")
        const { pipe } = require("fp-ts/function")

        const createHandlers = (locationClient) => ({
          register: async (req, res) => {
            await locationClient.addRoute({
              aor: Target.getTargetAOR(req),
              route: LocationHelper.createRoute(req),
              maxContacts: -1 // -1 means no limit
            })
            res.sendRegisterOk(req)
          },
          sendMessage: async (req, res) => {
            // Next step
          }
        })

        module.exports = { createHandlers }
        ```
      </Tab>
      <Tab title="Go">
        Create `handlers.go`. The `register` handler stores the sender's route in the Location Service under the target AOR and replies `200 OK` with the request's Contact. `processor.CreateRoute` builds the route from the request's top Via:

        ```go handlers.go
        package main

        import (
        	"context"
        	"log"

        	"github.com/fonoster/routr/pkg/processor"
        	"github.com/fonoster/routr/pkg/processor/pb/location"
        	"google.golang.org/grpc/codes"
        	"google.golang.org/grpc/status"
        )

        type handlers struct {
        	location location.LocationClient
        }

        func (h *handlers) register(ctx context.Context, req *processor.MessageRequest) (*processor.MessageResponse, error) {
        	_, err := h.location.AddRoute(ctx, &location.AddRouteRequest{
        		Aor:         processor.TargetAOR(req),
        		Route:       processor.CreateRoute(req, processor.DefaultExpires),
        		MaxContacts: -1, // -1 means no limit
        	})
        	if err != nil {
        		log.Println("unable to add the route:", err)
        		return processor.InternalServerError(), nil
        	}
        	return processor.RegisterOK(req, nil), nil
        }
        ```

        The imports include the ones the next step needs.
      </Tab>
    </Tabs>

    <Warning>
      Always pass `maxContacts` (`MaxContacts` in Go). Over gRPC an omitted value arrives as `0`, and the Location Service rejects new contacts once the AOR holds `0` or more of them. Use `-1` for no limit.
    </Warning>
  </Step>

  <Step title="Handle MESSAGE with the Alterations API">
    <Tabs>
      <Tab title="Node.js">
        Replace the `sendMessage` stub. It forwards responses back, looks up the callee, and builds the outgoing message by piping the request through [alterations](/reference/alterations-api). Each alteration takes a `MessageRequest` and returns a modified copy:

        ```javascript handlers.js
        sendMessage: async (req, res) => {
          // Responses go back unmodified, minus our own Via
          if (ProcessorHelper.isTypeResponse(req)) {
            return res.send(Alterations.removeTopVia(req))
          }

          const route = (
            await locationClient.findRoutes({
              aor: Target.getTargetAOR(req),
              callId: req.ref
            })
          )[0]

          // The callee isn't registered
          if (!route) return res.sendNotFound()

          // The callee is connected to another EdgePort: send the message there
          if (req.edgePortRef !== route.edgePortRef) {
            return res.send(
              pipe(
                req,
                Alterations.addSelfVia(route),
                Alterations.addSelfRecordRouteToPeer(route),
                Alterations.addRouteToPeerEdgePortOwnAddress(route),
                Alterations.addRouteToNextHop(route),
                Alterations.addXEdgePortRef,
                Alterations.decreaseMaxForwards
              )
            )
          }

          // The callee is connected to this EdgePort: deliver it
          return res.send(
            pipe(
              req,
              Alterations.decreaseMaxForwards,
              Alterations.removeAuthorization,
              Alterations.removeSelfRoutes,
              Alterations.removeXEdgePortRef,
              Alterations.addSelfVia(route),
              Alterations.addRouteToNextHop(route)
            )
          )
        }
        ```
      </Tab>
      <Tab title="Go">
        Add `sendMessage` to `handlers.go`. It forwards responses back, looks up the callee, and builds the outgoing message with [alterations](/reference/alterations-api). A Go alteration changes `req` in place, and the ones that can fail return an `error`:

        ```go handlers.go
        func (h *handlers) sendMessage(ctx context.Context, req *processor.MessageRequest) (*processor.MessageResponse, error) {
        	// Responses go back unmodified, minus our own Via
        	if processor.IsTypeResponse(req) {
        		processor.RemoveTopVia(req)
        		return processor.Forward(req), nil
        	}

        	found, err := h.location.FindRoutes(ctx, &location.FindRoutesRequest{
        		Aor:    processor.TargetAOR(req),
        		CallId: req.GetRef(),
        	})
        	// The callee isn't registered: the Location Service answers NotFound
        	if status.Code(err) == codes.NotFound || (err == nil && len(found.GetRoutes()) == 0) {
        		return processor.NotFound(), nil
        	}
        	if err != nil {
        		log.Println("unable to find the route:", err)
        		return processor.InternalServerError(), nil
        	}
        	route := found.GetRoutes()[0]

        	// The callee is connected to another EdgePort: send the message there
        	if req.GetEdgePortRef() != route.GetEdgePortRef() {
        		if err := processor.AddSelfVia(req, route); err != nil {
        			return processor.InternalServerError(), nil
        		}
        		if err := processor.AddSelfRecordRouteToPeer(req, route, nil); err != nil {
        			return processor.InternalServerError(), nil
        		}
        		if err := processor.AddRouteToPeerEdgePortOwnAddress(req, route); err != nil {
        			return processor.InternalServerError(), nil
        		}
        		processor.AddRouteToNextHop(req, route)
        		processor.AddXEdgePortRef(req)
        		processor.DecreaseMaxForwards(req)
        		return processor.Forward(req), nil
        	}

        	// The callee is connected to this EdgePort: deliver it
        	processor.DecreaseMaxForwards(req)
        	processor.RemoveAuthorization(req)
        	processor.RemoveSelfRoutes(req)
        	processor.RemoveXEdgePortRef(req)
        	if err := processor.AddSelfVia(req, route); err != nil {
        		return processor.InternalServerError(), nil
        	}
        	processor.AddRouteToNextHop(req, route)
        	return processor.Forward(req), nil
        }
        ```

        The Go functions are the Node.js ones with a capital first letter; the [Alterations API reference](/reference/alterations-api#summary) lists both names for every function.
      </Tab>
    </Tabs>

    The two branches implement [EdgePort cooperation](/concepts/edgeport-cooperation). The names below are the Node.js ones:

    - `addSelfVia(route)` adds a Via for the egress EdgePort interface.
    - `addSelfRecordRouteToPeer(route)` keeps this EdgePort in the path for the rest of the dialog, named by its own address toward the peer EdgePort.
    - `addRouteToPeerEdgePortOwnAddress(route)` adds a Route to the EdgePort that holds the callee's connection, at that EdgePort's own address when the two share a local network. EdgePorts behind one load balancer share its external address, and a Route to that address could reach any of them. See [Dialogs across EdgePorts](/reference/alterations-api#dialogs-across-edgeports).
    - `addRouteToNextHop(route)` adds a Route to the callee.
    - `addXEdgePortRef` adds the `X-Edgeport-Ref` header; `removeXEdgePortRef` strips it on the last hop.
    - `decreaseMaxForwards`, `removeAuthorization`, and `removeSelfRoutes` clean up the request before delivery.
  </Step>

## Register the processor in the Dispatcher

The Message Dispatcher sends each request to the first processor whose `matchFunc` returns `true` and whose `methods` include the request method. Order matters: put specific matches before catch-alls.

This `dispatcher.yaml` sends `MESSAGE` to the IM processor and everything else to Connect:

```yaml dispatcher.yaml
kind: MessageDispatcher
apiVersion: v2beta1
ref: message-dispatcher
spec:
  bindAddr: 0.0.0.0:51901
  processors:
    - ref: im-processor
      addr: im:51904
      matchFunc: req => req.method === "MESSAGE"
      methods:
        - MESSAGE
    - ref: connect-processor
      addr: connect:51904
      matchFunc: req => true
      methods:
        - REGISTER
        - INVITE
        - ACK
        - BYE
        - CANCEL
```

`matchFunc` is a JavaScript expression evaluated against the JSON `MessageRequest`. Other useful matches:

```javascript
req => req.message.from.address.uri.user === "alice"
req => req.message.extensions.find(e => e.name === "User-Agent" && e.value.includes("Zoiper"))
```

Set `addr` to wherever your processor runs. When you run from source, edit `config/dispatcher.yaml` and restart with `npm run start:dispatcher`. On Kubernetes, add the entry under `dispatcher.processors` in the [Helm values](/reference/helm-values).

<Note>
  The Dispatcher is optional. For a single processor you can point EdgePort's `spec.processor.addr` straight at it and list the methods it handles in `spec.methods`.
</Note>

## Verify

Register two softphones (for example Blink) against your EdgePort and send a chat message from one to the other. The message reaches the second phone, and the processor's console shows the requests it handled. A `MESSAGE` to an unregistered user returns `404 Not Found`.

## Pitfalls

- **Keep processors stateless.** Store state in the Location Service or the [API Server](/guides/custom-data-with-the-apiserver), not in memory, so you can run several replicas. On Kubernetes, put a Go processor's replicas behind a headless Service (`clusterIP: None`): the Dispatcher balances over the addresses the name resolves to, and the Go SDK's server ends each connection after about 5 minutes, so a new replica gets traffic within that time.
- **Answer every call.** In Node.js, a handler that throws without calling a `Response` method leaves the transaction hanging; wrap handlers in `try`/`catch` and call `sendInternalServerError()`. In Go, reject a message by returning a response function's result, such as `processor.InternalServerError()`, with a `nil` error. A returned `error` is not a SIP answer: the gRPC call fails with `Internal`, and the Dispatcher logs a warning and forwards the request unchanged, as if the Processor weren't there.
- **Node.js alterations don't mutate.** They return a deep copy, so always send the result of `pipe`, not the original `req`.
- **Go alterations change `req` in place.** The handler owns its request, so send `processor.Forward(req)` after them. Take a `proto.Clone` first if you need the original.
