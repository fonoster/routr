---

Turn on message recording for a Trunk, an Agent, a Peer or a Domain, and the Message Dispatcher writes every message of every call that touches it to one file per call. The file holds each message as the EdgePort received it, every component that touched it with its duration and what it changed, and the message as it left. Replay the file with `rctl trace replay`.

## When to record

- A carrier reports a header problem, for example two `P-Asserted-Identity` headers, and you need to see what the Connect processor sent.
- A call was rejected and the logs say `500` without saying which component answered.
- You are upgrading Routr and want to prove a scenario behaves the same before and after.

Recording costs one JSON line per message, written asynchronously after the answer went back to the EdgePort. It never blocks or fails a call: a write error is logged and the message continues on its way. Credentials (`Authorization`, `Proxy-Authorization`, `X-Gateway-Auth`, the digest response) are replaced with `REDACTED` before the record is written, unless `redact: false` is set for a test stack.

## Turn recording on

Recording is off by default. Enable it on the Dispatcher, then choose which calls to record.

<Tabs>
  <Tab title="Configuration file">
    Add a `recording` block to the Dispatcher's configuration file and mount a directory for the files:

    ```yaml
    kind: MessageDispatcher
    apiVersion: v2beta1
    ref: message-dispatcher
    spec:
      bindAddr: 0.0.0.0:51901
      recording:
        enabled: true
        path: /var/routr/traces
        mode: flagged
        redact: true
        lint:
          profiles: [sip]
      processors:
        - ref: connect-processor
          addr: connect:51904
          matchFunc: req => true
          methods: [REGISTER, MESSAGE, INVITE, ACK, BYE, CANCEL, REFER, NOTIFY]
    ```

    With Docker Compose, mount that file over `/etc/routr/dispatcher.yaml` and the directory over `/var/routr/traces`.
  </Tab>
  <Tab title="Kubernetes">
    With the release from [Deploy on Kubernetes](/guides/deploy-on-kubernetes), keep its current values and add the recording ones:

    ```bash
    helm upgrade sipnet routr/routr-connect --namespace sipnet --reuse-values \
      --set dispatcher.recording.enabled=true \
      --set dispatcher.recording.mode=flagged \
      --set 'dispatcher.recording.lint.profiles={sip}'
    ```

    The chart renders the block into the Dispatcher's ConfigMap. Files go to an `emptyDir` unless you set `dispatcher.recording.existingClaim` to a PersistentVolumeClaim.
  </Tab>
  <Tab title="routr-one">
    Add a `recording` block under `spec` in `/etc/routr/one.yaml`, the file routr-one 2.31.0 and later read (see [Configure the container](/guides/deploy-with-docker#configure-the-container)):

    ```yaml one.yaml
    kind: RoutrOne
    apiVersion: v2beta1
    ref: routr-one
    spec:
      recording:
        enabled: true
        path: /var/routr/traces
        mode: flagged
        redact: true
        lint:
          profiles: [sip]
        maxRecordsPerCall: 1000
        maxCalls: 10000
    ```

    `enabled` and `path` are required: the block fails validation without them, and the file has no default `path`. `mode` defaults to `flagged` and `redact` to `true`.

    Routr runs as the user `fonoster` (UID `5000`), and the image doesn't create `/var/routr/traces`. Mount a directory that user can write at `recording.path`, or the container fails to start:

    ```yaml compose.yaml
    services:
      routr:
        volumes:
          - ./one.yaml:/etc/routr/one.yaml:ro
          - ./traces:/var/routr/traces
    ```

    ```bash
    mkdir traces && sudo chown 5000:5000 traces
    ```

    <Note>
    `RECORD_MESSAGES` (`true` to turn recording on), `RECORD_MESSAGES_MODE` and `RECORD_MESSAGES_PATH` still work, but they are deprecated in favor of `spec.recording.enabled`, `spec.recording.mode` and `spec.recording.path`. With only the variables, credentials are always redacted and no rules are evaluated.
    </Note>
  </Tab>
</Tabs>

Two modes:

| Mode | Records |
| --- | --- |
| `flagged` (default) | Calls that touch a Trunk, Agent, Peer or Domain whose `trace.enabled` is `true`. The Connect processor flags the call on the first routed message (or on a REGISTER of a flagged Agent or Peer); the Dispatcher then records every later message of the same Call-ID until the call has been idle for two hours. |
| `all` | Every call. Use it on a test stack, for example the compliance suite in CI, not in production. |

Set `trace.enabled` on the resource, in YAML or through the API:

```yaml
- apiVersion: v2beta1
  kind: Trunk
  ref: trunk-01
  spec:
    trace:
      enabled: true
```

A Trunk records the calls of one provider; an Agent its calls and registrations; a Domain every call of that customer.

## Files

One file per call in the Dispatcher's `recording.path` (`spec.recording.path` in routr-one), named by the time of the first recorded message and the Call-ID, for example `20261023T024110321Z-1-25_10.111.221.22.jsonl`. Each line is one record; `rctl trace validate <file>` checks that a file is complete and readable by your `rctl`.

The Dispatcher stops writing a call after 1 000 records and stops starting new recordings when 10 000 calls are active. Both limits are configurable (`maxRecordsPerCall`, `maxCalls`) in the `recording` block of the configuration file.

## Replay a call in the terminal

<img
  className="rounded-xl"
  src="/images/record-and-replay/replay.gif"
  alt="rctl trace replay opening a recording: the r. mark blinks on the splash, moves into the header, then the Summary, Ladder, Path and Compare views appear in turn with messages drawn between the caller, the EdgePort and the provider"
/>

Open a recording with `rctl trace replay`. The examples on this page use two recordings of SIPconnect 1.1 test 1.3.1 from the repository's corpus: agent 1001 calls `17853178070` through the trunk `sip.provider.net`, and agent 1002 places the same call.

```bash
rctl trace replay etc/corpus/seet-agent-1001_sc-1.3.1-dod-invite_provider_20261023.jsonl --sip-connect
```

The viewer opens with a short splash: the `r.` mark with its dot blinking and the name of the file being read. It lasts five seconds; press any key to skip it. When you open the viewer on a record with `--select`, there is no splash.

### Read the header

Every view shares the same three header lines, with the `r.` mark on the left:

- **trace** names the file, or both files when you compare, and pins the verdict for the call on the right.
- **call** shows the Call-ID and when the first message was recorded, in UTC.
- **edgeport** shows the EdgePort that received the call and its version, the Dispatcher version, and how many messages were recorded.

The verdict sums up the whole call in a word:

| Verdict | Means |
| --- | --- |
| `FORWARDED 8.8 ms` | Routr forwarded the call. The time is how long the first forwarded INVITE spent inside Routr. |
| `REJECTED 500` | A component answered a message with a failure, or failed itself. The status is the first one, and the Summary says at what offset and from which trunk. A `401` or `407` challenge is not a rejection. |
| `ANSWERED 200` | Routr answered the request itself, for example the `200` to a REGISTER. |
| `CHALLENGED 401` | Routr asked for credentials and the recording ends there. |
| `DROPPED` | No message left Routr. |
| `INCOMPLETE` | No line of the file could be read. When only the last line is cut, the verdict says `· incomplete` and the status bar tells you how many records were read. |

Below the header, the tab row shows the four views. The bottom line lists the keys for the current view and, on the right, where you are, for example `msg 2/7  +23 ms`.

### Summary

<img
  className="rounded-xl"
  src="/images/record-and-replay/summary-dark.png"
  alt="Summary view of the agent 1001 call: FORWARDED 8.8 ms, 7 messages, 0 rejected, 1 check failed; facts for the call, Call-ID, direction agent-to-pstn, trunk sip.provider.net, EdgePort, Dispatcher, recording time and identity; and the checks on the first forwarded INVITE, with the failed Request-URI check selected"
/>

The Summary answers "what happened to this call" before you look at any message. Press `1` to come back to it.

The first line repeats the verdict with the message counts. **FACTS** lists who called whom, the Call-ID, the direction and trunk the Connect processor chose, the EdgePort and Dispatcher that handled the call, when it was recorded, and the identity sent to the far side (`P-Asserted-Identity`), when there is one.

**CHECKS** shows the rule findings on the first INVITE that Routr forwarded:

| Mark | Means |
| --- | --- |
| `✗` | A rule failed, for example `Request-URI user 17853178070 is not E.164`. |
| `!` | A warning, for example `Contact names 10.111.221.22, an internal address the far side cannot reach`. |
| `✓` | How many rules passed, for example `13 of 17 sip + sip-connect rules passed`. |
| `–` | No INVITE was forwarded, so the checks do not apply. |

Press `n` and `N` to move between failed and warned checks. The status bar then shows the rule id and the spec it comes from, so you can look it up. The `sip` rules always run. The `sip-connect` rules run only with `--sip-connect`: without it, the same call shows `2 warnings` instead of `1 check failed`, because the E.164 Request-URI rule belongs to SIPconnect. When the call holds more than one forwarded INVITE, for example a re-INVITE, the **CHECKS** line says how many more there are.

### Ladder

<img
  className="rounded-xl"
  src="/images/record-and-replay/ladder-dark.png"
  alt="Ladder view: lanes for 1001, the EdgePort 2c339a0d50cd and sip.provider.net with a vertical rail under each; the second INVITE is selected and open, showing its hops dispatcher matched and connect-processor forwarded under the EdgePort rail; the detail pane on the right shows the incoming INVITE headers and the hop list"
/>

Press `2` for the Ladder: every message of the call, in order, between the parties that sent and received it.

- **Lanes.** Each party gets a lane with a vertical rail: the caller on the left, the EdgePort in the middle in teal, and the far side on the right. Under each title is the address it used, when there is room.
- **Arrows.** A solid arrow is a request, a dashed arrow is a response. Each message has two legs: the leg that reached Routr, and the leg that left it. The outgoing leg's label adds the number of hops and the time spent in Routr, for example `INVITE c2 · 2 hops 8.8ms`. `c2` is the CSeq number.
- **Marks.** The column left of the time explains rows that did not go straight through. `?` marks a `401` or `407` challenge. `✗` marks a message a component rejected or failed on; its answer is drawn in red. `·` marks a message that stopped at Routr, because Routr answered it itself or dropped it; its arrow ends in a bar (`┤`) on the EdgePort rail instead of an arrowhead. `=` marks a retransmission.
- **Time.** The time column shows the offset from the first message, for example `+23` (milliseconds). Press `t` to switch to the time since the previous message (`Δ`) and to the wall clock in UTC. Offsets past ten seconds keep their unit, such as `12.3s` or `1m05s`. A silence of more than two seconds between messages gets its own row, `· · · 3.1 s · · ·`, so long pauses stand out.
- **Retransmissions.** Identical retransmissions are folded into the first copy, which shows `×3` for three copies. Press `x` to show each copy on its own row.

Select a message with `j` and `k` (or the arrow keys); `g` and `G` jump to the first and last message, and `Ctrl-D` and `Ctrl-U` move half a page.

#### Hops

Press `Enter` on a message to open its hops under the EdgePort rail, and again to close them. Each line is one component that handled the message, in order:

```text
├ dispatcher         0ms  matched
├ connect-processor  8.4ms  forwarded  +5 −1 ~4
└ 8.8ms
```

The line gives the component, how long it took, and what it did: `matched` (the Dispatcher picked a processor), `pass-through` (a middleware returned the message unchanged), `forwarded`, `responded` (the component answered the request), `relayed` (a response going back), or `error`. The counts are the headers that component added (`+`), removed (`−`) and changed (`~`); the Request-URI counts as a change. The last line is the total time in Routr. A component's error message is printed under its line in red.

#### Detail pane

The detail pane shows the selected message. Press `d` to switch between two modes:

- **Headers.** The request line or status line, where the message came in and where it went (`in 10.111.221.22:5647/UDP → 0.0.0.0:5060`, `out 10.111.220.2:5060 → sip.provider.net:7060`), the headers as received, and the hop list. Credentials show as `… (redacted)`. For a request Routr answered itself, the out line says the reply went back to the sender, for example `out 401 back to 10.111.221.22:5647/UDP`.
- **Diff.** Every change between the message that came in and the one that left, with the component that made it: the rewritten Request-URI, `Max-Forwards 70 → 69`, the Via Routr added, and headers such as `P-Asserted-Identity` and `Record-Route` added by the Connect processor.

Press `p` to hide or show the pane. Where it sits depends on the width of your terminal; see [Terminal size and colours](#terminal-size-and-colours).

#### Filter and problems

Press `/` and type to show only some messages, then `Enter` to apply it and `Esc` to clear it. A filter can be a method (`invite`), a status (`500`), a status class (`5xx`), or an outcome (`rejected`, `forwarded`, `relayed`, `answered`, `error`). Any other text matches the message label.

In the Ladder, `n` and `N` jump to the next or previous problem, which is any message that was rejected or failed. Challenges do not count.

### Path

<img
  className="rounded-xl"
  src="/images/record-and-replay/path-dark.png"
  alt="Path view of the first forwarded INVITE: boxes for 1001, the EdgePort and sip.provider.net joined by arrows labelled INVITE and INVITE rewritten; then the Request-URI before and after, the Via stack with Routr's own Via marked ours, added on egress, the route set with the added Record-Route, and notes"
/>

Press `3` for the Path: how the first forwarded INVITE crossed Routr, read from top to bottom.

- **The three boxes** are the caller (its address, and whether it is inside the local network), the EdgePort (the address it received on and the one it sent from), and the far side (the host and port the request went to, and the address that resolved to).
- **REQUEST-URI** shows the Request-URI as it came in and as it left: here `sip:17853178070@sip.local:-1;transport=udp` became `sip:17853178070@sip.provider.net:7060;transport=udp`.
- **VIA STACK, TOP FIRST** lists the Via headers of the outgoing request. The top one is marked `ours, added on egress`; the ones below belong to the caller.
- **ROUTE SET** shows the Route headers in and out, and the Record-Route Routr added.
- **NOTES** points out what deserves a look, for example a Record-Route that names an internal interface the far side cannot reach, and confirms what went as expected, such as `Max-Forwards 70 → 69`.

When no message was forwarded, the Path says so and names the component that answered, with its status or error.

### Compare

<img
  className="rounded-xl"
  src="/images/record-and-replay/compare-dark.png"
  alt="Compare view of the agent 1001 and agent 1002 recordings: both files with their date, Routr version, outcome and message count; a summary that 6 of 7 rows differ; then the two calls side by side, row by row, with ≠ on the rows that differ and the third row selected"
/>

Compare lines up two recordings of the same scenario, for example a call before and after an upgrade, or the same call placed by two agents:

```bash
rctl trace replay etc/corpus/seet-agent-1001_sc-1.3.1-dod-invite_provider_20261023.jsonl \
  --compare etc/corpus/seet-agent-1002_sc-1.3.1-dod-invite_provider_20261023.jsonl
```

Press `4` for the Compare view. The top lines name file `A` and file `B` with their date, Routr version, outcome and number of messages, then sum up the differences: `≠ 6 of 7 rows differ · 0 only in A · 0 only in B`.

The two files are lined up by kind, method, CSeq and status, so a message missing from one side shows as a gap instead of shifting everything after it. Each row has a mark:

| Mark | Means |
| --- | --- |
| `≠` | The message is in both files, and Routr handled it differently. |
| `−` | The message is only in file A. |
| `+` | The message is only in file B. |

A row differs when its outcome, status, number of hops or outgoing headers differ. Compare looks at what Routr did, not at what changes on every call: Via branches, tags, digest nonces, the Call-ID and the caller's source port are ignored. Timing is shown but never counts. In this example every forwarded row differs for one reason, the `From` header: one call comes from `1001`, the other from `1002`.

Select a row and press `d` to open it in the Ladder with the A/B diff in the detail pane. In the Ladder, `c` adds a column that compares each message with file B: `=` the same, `≠` different, `−` only in A. Messages only file B has are slotted in as `(B)` rows marked `+`. At 160 columns and wider, Compare also prints the reason under each row that differs.

### Terminal size and colours

The viewer needs a terminal of at least 80 columns by 24 rows, and redraws when you resize it. The layout adapts to the width:

| Width | Layout |
| --- | --- |
| 80 to 99 columns | The Ladder uses the full width and the detail pane is hidden; `p` opens it under the ladder. Compare stacks the A and B lines of each row. |
| 100 to 119 columns | The detail pane sits under the ladder. Compare still stacks A and B. |
| 120 to 159 columns | The detail pane sits on the right, next to the ladder. Compare shows A and B side by side. |
| 160 columns and wider | A wider detail pane, and Compare explains each difference on its own line. |

When the viewer starts, it asks the terminal for its background colour and picks a palette to match. If the terminal does not answer, it reads `COLORFGBG`, and otherwise uses the dark palette. On a light background, the accents are darker and the selected row is a pale bar, so the text stays readable:

<img
  className="rounded-xl"
  src="/images/record-and-replay/ladder-light.png"

The palette is chosen once, at startup. If you switch your terminal theme, open the recording again. The viewer draws with box-drawing characters and arrows; `--ascii` uses plain ASCII instead, which it also does by itself when `TERM=dumb` or the locale is not UTF-8.

## Print a call for an issue or CI

```bash
rctl trace replay etc/corpus/seet-agent-1001_sc-1.3.1-dod-invite_provider_20261023.jsonl --static --view ladder --select 2
```

`--static` prints pages of plain text and exits, with no colour and no cursor movement, so the output reads in a GitHub issue, a pager or a CI log. Static mode is implied when stdout is not a terminal, and by `--view all`.

| View | Prints |
| --- | --- |
| `summary` (default) | The verdict, facts and checks, then the ladder. |
| `ladder` | The ladder. With `--select <seq>`, it opens that record's hops and adds its headers and its diff. Without it, the first forwarded INVITE's headers and diff are added. |
| `path` | The Path view. |
| `compare` | The Compare view, then the header diff of every row that differs. |
| `all` | Every page, one after the other. |

Pages are as wide as your terminal, or `100` columns when there is none; `--columns` sets the width, between `80` and `120`. `--fail-on` turns a recording into a test: with `rejected`, the command exits `4` when the call has a rejected message; with `warning`, also when a check failed or warned. The agent 1001 call passes `--fail-on rejected` and exits `4` with `--fail-on warning --sip-connect`.

| Exit code | Means |
| --- | --- |
| `0` | Printed. |
| `1` | Usage error. |
| `2` | The file cannot be read or has no records. |
| `3` | The file uses a trace version this `rctl` does not read. |
| `4` | The `--fail-on` condition is met. |

## Check a recording against the specs

```bash
rctl trace lint call.jsonl --sip-connect
```

Every record is evaluated by a set of rules, one pure function each, that read only the SIP messages and what the Dispatcher measured. Two profiles:

| Profile | Rules | When |
| --- | --- | --- |
| `sip` | RFC 3261 and companions: Max-Forwards decremented, the proxy's Via on top and removed on the way back, Record-Route and Route pointing at the proxy, accepted credentials not forwarded, internal addresses not leaving through the external interface, a 200 to REGISTER with its binding, CSeq order, CANCEL and ACK matching their INVITE, a 2xx acknowledged before BYE, retransmissions. | Always. |
| `sip-connect` | SIPconnect 1.1 on the INVITE that leaves through the external interface: one P-Asserted-Identity, E.164 with `user=phone`, an E.164 Request-URI, From E.164 or anonymous, `Privacy: id` honoured. | `--sip-connect`, because not every deployment faces a SIPconnect provider. |

Each finding names the rule, cites the spec, and points at the side (`in`, `out` or the whole call) and header. The Summary view shows the findings on the first forwarded INVITE; `--fail-on warning` turns them into an exit code for CI.

The Dispatcher can evaluate the same rules as it writes: set `recording.lint.profiles`. Each finding is then logged as a warning with the Call-ID, seq and rule, and written on the record under `findings`, so a recording carries what the proxy thought at the time.

A component may annotate its hop with `trace.`-prefixed metadata keys (the Connect processor adds `direction` and `trunk`). The Dispatcher copies them into the hop's `metadata` and strips them before the message leaves. Routr draws no conclusion from them, since components are swappable; they are there for people and tools reading the file.

## Keep a known-good corpus

A recording of a call that behaved as it should is worth keeping: replayed through the chain after a change, it proves the chain still answers the same way. The repository keeps the SEET compliance recordings under `etc/corpus` and each partner interconnect's recordings under `interop/<partner>/`, with that folder's own `manifest.yaml`. `npm run compat` replays `etc/corpus` and every `interop/*/manifest.yaml` through the Node services started from the checkout, with no EdgePort and no Docker, on every pull request. Any message whose outcome or outgoing headers drifted fails the build, and so does a rule finding a file did not have.

Files are named `<origin>_<flow>_<far-end>_<YYYYMMDD>.jsonl`: who sent the first message, what happened, who was on the other side, when. Adding a known-good is four steps:

1. Take the file from the `call-recordings` artifact of a compliance run, or from your own stack.
2. `rctl trace sanitize <file> --credentials etc/corpus/resources/credentials.yaml --rewrite <real>=<test> ... --out etc/corpus/<name>.jsonl` (`interop/<partner>/<name>.jsonl` for a partner interconnect). The digest responses are recomputed with the test password, so the file still authenticates; the rewrites replace real numbers and hosts everywhere in the file.
3. Add the Trunk, Number, Agent or Credentials the recording touches to `etc/corpus/resources` if they are not there. Resources stay there for every replay, partner recordings included.
4. Add a line to `etc/corpus/manifest.yaml` (or to `interop/<partner>/manifest.yaml`), with `profiles: [sip-connect]` when the file faces a provider, and `findings` listing the rule ids the recording is known to trip (`rctl trace lint` prints them). A known-good describes what the chain does with real traffic; a finding that appears later is a regression, one that disappears is a change to declare.

The README in that directory has the details.

## Resend a message to a fix

```bash
rctl trace send call.jsonl --seq 7 --to localhost:51901
```

Sends the recorded message with `seq` 7 to a running Dispatcher (or straight to a processor on `51904`) and prints how the live answer differs from the recorded one. Via branches, tags and nonces differ between runs by design and never count. Credentials redacted at recording time come back as a challenge, which is itself the expected answer.
