Turn on message recording for a Trunk, and the Message Dispatcher writes every message of every call through that Trunk to one file per call. The file holds each message as the EdgePort received it, every component that touched it with its duration and what it changed, and the message as it left. Replay the file with `rctl trace replay`.

## When to record

- A carrier reports a header problem, for example two `P-Asserted-Identity` headers, and you need to see what the Connect processor sent.
- A call was rejected and the logs say `500` without saying which component answered.
- You are upgrading Routr and want to prove a scenario behaves the same before and after.

Recording costs one JSON line per message, written asynchronously. It never blocks or fails a call: a write error is logged and the message continues on its way. Credentials (`Authorization`, `Proxy-Authorization`, `X-Gateway-Auth`, the digest response) are replaced with `REDACTED` before the record is written.

## Turn recording on

Recording is off by default. Enable it on the Dispatcher, then choose which calls to record.

<Tabs>
  <Tab title="Docker">
    Set the variables on the `dispatcher` service (or on `routr-one`) and mount a directory for the files:

    ```yaml
    dispatcher:
      environment:
        RECORD_MESSAGES: "true"
        RECORD_MESSAGES_MODE: flagged
        RECORD_MESSAGES_PATH: /var/routr/traces
      volumes:
        - ./traces:/var/routr/traces
    ```
  </Tab>
  <Tab title="Kubernetes">
    ```bash
    helm upgrade routr routr/routr-connect \
      --set dispatcher.recording.enabled=true \
      --set dispatcher.recording.mode=flagged
    ```

    Files go to an `emptyDir` unless you set `dispatcher.recording.existingClaim` to a PersistentVolumeClaim.
  </Tab>
  <Tab title="Configuration file">
    ```yaml
    kind: MessageDispatcher
    apiVersion: v2beta1
    ref: message-dispatcher
    spec:
      bindAddr: 0.0.0.0:51901
      recording:
        enabled: true
        path: /var/routr/traces
        mode: flagged
      processors:
        - ref: connect-processor
          addr: connect:51904
          matchFunc: req => true
          methods: [REGISTER, MESSAGE, INVITE, ACK, BYE, CANCEL, REFER, NOTIFY]
    ```
  </Tab>
</Tabs>

Two modes:

| Mode | Records |
| --- | --- |
| `flagged` (default) | Calls through a Trunk whose `extended.recordMessages` is `true`. The Connect processor flags the call on the first routed message; the Dispatcher then records every later message of the same Call-ID until the call has been idle for two hours. |
| `all` | Every call. Use it on a test stack, for example the compliance suite in CI, not in production. |

To flag a Trunk, set the extended attribute:

```bash
rctl trunks update <ref>   # or through the SDK: extended: { recordMessages: true }
```

Through the API the Trunk's `extended` object accepts any attribute; `recordMessages: true` is the one the Connect processor reads.

## Files

One file per call in `RECORD_MESSAGES_PATH`, named by the time of the first recorded message and the Call-ID, for example `20261023T024110321Z-1-25_10.111.221.22.jsonl`. Each line is one record; `rctl trace validate <file>` checks that a file is complete and readable by your `rctl`.

The Dispatcher stops writing a call after 1 000 records and stops starting new recordings when 10 000 calls are active. Both limits are configurable (`maxRecordsPerCall`, `maxCalls`) in the `recording` block of the configuration file.

## Replay a call

```bash
rctl trace replay 20261023T024110321Z-1-25_10.111.221.22.jsonl
```

The viewer opens on the **Summary**: the verdict (`FORWARDED 16.1 ms` or `REJECTED 500 at +1681 ms`), the SIP Connect checks on the first forwarded INVITE, and the call facts. Press `2` for the **Ladder**: every message with both legs, solid arrows for requests and dashed for responses; select a message with `j`/`k`, press `Enter` to open its hop list inline, and `d` to switch the detail pane between the incoming headers and the diff of what left. `3` is the **Path**: who sat where, what the proxy rewrote. `n` jumps to the next problem. `?` lists every key.

The viewer needs an 80×20 terminal and reacts to resizing. Under `NO_COLOR` or `TERM=dumb` it draws with glyphs only, and `--ascii` forces the ASCII set.

## Paste it into an issue

```bash
rctl trace replay call.jsonl --static --view ladder --select 2
```

`--static` prints one page and exits, with no colour or boxes, never wider than 120 columns, so it reads in a GitHub issue or a CI log. `--view all` prints every page. When stdout is not a terminal, static mode is implied. `--fail-on rejected` makes the command exit `4` when the call has a rejected message, which turns a recording into a test.

## Compare two recordings

```bash
rctl trace replay call-after-upgrade.jsonl --compare call-before-upgrade.jsonl
```

`4` opens the **Compare** view: the two files lined up by method and CSeq, with `≠` on rows whose outcome, status, hop count or outgoing headers differ, and `−`/`+` on rows present in only one file. In the Ladder, `c` overlays the agreement column on the first file. Timing is shown but never counts as a difference.

## Resend a message to a fix

```bash
rctl trace send call.jsonl --seq 7 --to localhost:51901
```

Sends the recorded message with `seq` 7 to a running Dispatcher (or straight to a processor on `51904`) and prints how the live answer differs from the recorded one. Credentials were redacted at recording time, so a message that needed them comes back as a challenge, which is itself the expected answer.
