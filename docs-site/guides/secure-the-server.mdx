title: "Secure the server"
description: "For operators exposing Routr beyond a test network: turn on TLS for the API Server and SIP signaling, install certificates, and connect clients over TLS."
---

Encrypt the two channels that carry credentials: the API Server (port `51908`, used by `rctl` and the SDK) and SIP signaling (TLS on `5061`, WSS on `5063`). This guide uses the `fonoster/routr-one` image. Notes for split deployments and Kubernetes follow at the end.

<Note>
TLS protects signaling only. Routr is not a media server and doesn't encrypt RTP. Media encryption, if any, is negotiated between the endpoints.
</Note>

## Prerequisites

- A running routr-one container. See [Deploy with Docker](/guides/deploy-with-docker).
- OpenSSL, if you generate your own certificates.
- A DNS name for the server if you use certificates from a public CA.

## How Routr uses certificates

Both services read certificates from `/etc/routr/certs` inside the container.

| File | Used by | Purpose |
| --- | --- | --- |
| `server.crt` | API Server, EdgePort | Server certificate. |
| `server.key` | API Server, EdgePort | Private key for `server.crt`. |
| `ca.crt` | API Server, EdgePort | Optional. Appended to build the full chain, and used to verify client certificates when `VERIFY_CLIENT_CERT=true`. |
| `signaling.p12` | EdgePort | PKCS#12 keystore built at startup from the files above. |

At startup, the container converts `server.crt` and `server.key` into `signaling.p12`, protected by `PKCS12_PASSWORD`. If `server.crt` or `server.key` is missing, the container generates a self-signed pair first.

## Secure the server

<Steps>
  <Step title="Get a certificate">
    Use a certificate from a trusted CA (for example, Let's Encrypt) for production. Browsers and many softphones reject self-signed certificates.

    For development, generate a CA and a server certificate signed by it. Set the `CN` to the host name clients use.

    ```bash
    openssl genrsa -out ca.key 2048
    openssl req -new -x509 -key ca.key -out ca.crt -subj "/CN=My Test CA"
    openssl genrsa -out server.key 2048
    openssl req -new -key server.key -out server.csr -subj "/CN=localhost"
    openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out server.crt
    ```

    <Tip>
    In a clone of the Routr repository, `npm run generate:certs` runs the same commands and writes the files to `.certs/`.
    </Tip>
  </Step>
  <Step title="Mount the certificates and turn on TLS">
    Mount the files individually into `/etc/routr/certs`, set `TLS_ON` to enable TLS on the API Server, and publish the TLS ports. The following `compose.yaml` shows the full service.

    ```yaml compose.yaml
    services:
      routr:
        image: fonoster/routr-one:latest
        environment:
          EXTERNAL_ADDRS: ${DOCKER_HOST_ADDRESS}
          TLS_ON: "true"
          PKCS12_PASSWORD: ${PKCS12_PASSWORD}
        ports:
          - 51908:51908
          - 5060:5060/udp
          - 5061:5061
          - 5063:5063
        volumes:
          - shared:/var/lib/postgresql/data
          - ./server.crt:/etc/routr/certs/server.crt
          - ./server.key:/etc/routr/certs/server.key
          - ./ca.crt:/etc/routr/certs/ca.crt

    volumes:
      shared:
    ```

    Mount files, not the whole directory. The container writes `signaling.p12` into `/etc/routr/certs` and needs that directory to stay writable. Leave out the `ca.crt` line if your CA bundle is already in `server.crt`.
  </Step>
  <Step title="Restart the server">
    Recreate the container so it rebuilds the keystore.

    ```bash
    DOCKER_HOST_ADDRESS=192.168.1.3 PKCS12_PASSWORD=use-a-strong-password docker compose up -d
    ```
  </Step>
  <Step title="Verify SIP over TLS">
    Open a TLS connection to the signaling port. Replace the address with your server's.

    ```bash
    openssl s_client -connect 192.168.1.3:5061
    ```

    <Check>The output shows your certificate chain and a completed handshake.</Check>
  </Step>
  <Step title="Connect rctl over TLS">
    Drop the `--insecure` flag. With a self-signed certificate, pass your CA with `--cacert`. With a certificate from a trusted CA, no flag is needed. The host in `--endpoint` must match the certificate's `CN`.

    ```bash
    rctl domains get --endpoint localhost:51908 --cacert ./ca.crt
    ```

    The SDK takes the same settings through the `cacert` option. See [Manage resources with the Node.js SDK](/guides/manage-resources-with-the-sdk).
  </Step>
</Steps>

## Configure a softphone for TLS

Point the softphone's outbound proxy at port `5061` with `transport=tls`. The exact field name depends on the softphone. In Blink Pro, open the account, choose **Advanced** > **SIP Signaling**, and set **Primary Proxy** to `<host>:5061;transport=tls`.

## Choose TLS versions and cipher suites

The EdgePort uses TLS 1.3 only, on both the TLS and WSS transports. That applies to connections from phones and to the connections the EdgePort opens to carriers and peers. If a phone or carrier doesn't support TLS 1.3, enable TLS 1.2 as well:

- **routr-one or the EdgePort image:** set `SECURITY_CONTEXT_CLIENT_PROTOCOLS=TLSv1.3,TLSv1.2`.
- **`edgeport.yaml`:** set `spec.securityContext.client.protocols` to `[TLSv1.3, TLSv1.2]`.
- **Helm:** set `edgeport.tls.protocols` to `[TLSv1.3, TLSv1.2]`.

TLS 1.2 then uses ECDHE suites with AES-GCM or ChaCha20 only. To change the cipher suites, set `SECURITY_CONTEXT_CLIENT_CIPHER_SUITES`, `spec.securityContext.client.cipherSuites`, or `edgeport.tls.cipherSuites`. See [EdgePort](/reference/components/edgeport#configuration-file) for the default list.

To check what the EdgePort accepts, run `openssl s_client -connect <host>:5061 -tls1_3`. A working connection prints `New, TLSv1.3`.

## Call a carrier over TLS

A trunk whose outbound URI has `transport: tls` makes the EdgePort open a TLS connection to the carrier for every call that leaves through it. Three things must be true:

1. The EdgePort has a `tls` transport and a `spec.securityContext` with a keystore, as set up above. The connection to the carrier leaves from that listening point. Without it the call gets `502 Bad Gateway` and the Connect processor logs `no listening point found for transport TLS`.
2. The EdgePort trusts the carrier's certificate. With `client.authType: DisabledAll`, the default in the examples, JAIN-SIP skips certificate validation on the connections the EdgePort opens, so any carrier certificate is accepted. With any other `authType`, the carrier's certificate is checked against the truststore: leave `spec.securityContext.trustStore` unset so the JVM's public CAs apply, set it only to trust a private CA, and never point it at `signaling.p12`.
3. The TLS versions overlap. Most carriers negotiate TLS 1.2, so enable it as shown in [Choose TLS versions and cipher suites](#choose-tls-versions-and-cipher-suites).

Carriers that require TLS usually require SRTP as well. The media relay does not negotiate SRTP toward a trunk yet, so such a carrier will still reject the media.

## Require client certificates (optional)

To make the API Server accept only clients with a certificate signed by your CA, mount `ca.crt` and set `VERIFY_CLIENT_CERT` to `"true"`. Clients must then present a certificate on every connection.

## Other deployments

- **Split Docker deployment.** The `fonoster/routr-edgeport` image builds `signaling.p12` from `/etc/routr/certs/server.crt` and `server.key` at startup, the same way routr-one does. Point `spec.securityContext` in `edgeport.yaml` at the keystore. To build a keystore by hand, run `.scripts/convert-to-p12.sh <cert-dir> <password>` from the repository; `npm run convert:certs` runs it and moves the result to `etc/certs/`.
- **Kubernetes.** `apiserver.tlsOn` defaults to `true` and `edgeport.transport.tls.enabled` turns on SIP over TLS. Change `edgeport.pkcs12Password` from its default. The chart has no value for mounting your own certificate, so the containers generate self-signed certificates at startup. See [Helm values](/reference/helm-values).

<Warning>
The `fonoster/routr-pgdata` image regenerates `server.crt` and `server.key` every time it starts. Certificates you mount at those paths in that image are overwritten or, if mounted read-only, make the container fail to start.
</Warning>

## Troubleshooting

- **`rctl` reports a certificate error.** The endpoint host doesn't match the certificate's `CN`, or you used a self-signed certificate without `--cacert`.
- **A phone or a TLS trunk fails the TLS handshake.** It probably doesn't support TLS 1.3. Enable TLS 1.2 as shown in [Choose TLS versions and cipher suites](#choose-tls-versions-and-cipher-suites).
- **A call to a TLS trunk fails the handshake with a certificate error.** The EdgePort doesn't trust the carrier's certificate. Remove `spec.securityContext.trustStore` so the JVM's public CAs apply, or point it at a truststore that holds the carrier's CA.
- **Browsers refuse the WSS connection.** Use a certificate from a trusted CA. See [Enable WebRTC clients](/guides/enable-webrtc).
- **The EdgePort fails to load the keystore.** `PKCS12_PASSWORD` must be the same value the keystore was built with. Recreate the container after changing it.
