Two channels carry credentials: the Data API (port `51907`, used by `rctl` and the SDK) and SIP signaling (TLS on `5061`, WSS on `5063`). This guide secures both on the `fonoster/routr-one` image, configured with `/etc/routr/routr.yaml`. Notes for split deployments and Kubernetes follow at the end.

<Note>
TLS protects signaling. Routr is not a media server and never touches RTP itself. With RTPEngine in the path (see [RTPRelay](/reference/components/rtprelay)), media toward a trunk that uses TLS is encrypted with SRTP; otherwise media encryption, if any, is negotiated between the endpoints.
</Note>

## Prerequisites

- A running routr-one container with a `routr.yaml`. See [Deploy with Docker](/guides/deploy-with-docker).
- OpenSSL, if you generate your own certificates.
- A DNS name for the server if you use certificates from a public CA.

## How Routr uses certificates

The certificates live in `/etc/routr/certs` inside the container.

| File | Used by | Purpose |
| --- | --- | --- |
| `server.crt` | Data API, EdgePort | Server certificate. |
| `server.key` | Data API, EdgePort | Private key for `server.crt`. |
| `ca.crt` | EdgePort, `rctl` | Optional. Appended to the EdgePort's chain; also the CA `rctl` verifies the Data API with. |
| `signaling.p12` | EdgePort | PKCS#12 keystore built at startup from the files above. |

At startup, the image's script converts `server.crt` and `server.key` into `signaling.p12`, protected by the `PKCS12_PASSWORD` variable (`changeme` by default). If `server.crt` or `server.key` is missing, it generates a self-signed pair first. Routr itself doesn't read `PKCS12_PASSWORD`: set `spec.edgeport.securityContext.keyStorePassword` to the same value.

The Data API reads `server.crt` and `server.key` directly, from the paths in `spec.data.tls`.

## Secure the server

<Steps>
  <Step title="Get a certificate">
    Use a certificate from a trusted CA (for example, Let's Encrypt) for production. Browsers and many softphones reject self-signed certificates.

    For development, generate a CA and a server certificate signed by it. Set the `CN` to the host name clients use.

    ```bash
    openssl genrsa -out ca.key 2048
    openssl req -new -x509 -key ca.key -out ca.crt -subj "/CN=My Test CA"
    openssl genrsa -out server.key 2048
    openssl req -new -key server.key -out server.csr -subj "/CN=localhost"
    openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out server.crt
    ```

    <Tip>
    In a clone of the Routr repository, `npm run generate:certs` runs the same commands and writes the files to `.certs/`.
    </Tip>
  </Step>
  <Step title="Generate an API key">
    The Data API accepts callers that send a key it knows. Any long random string works.

    ```bash
    openssl rand -hex 32
    ```

    Keep it in your secret store, and pass it to the container as `ROUTR_API_KEY`. The file names the variable; the key itself never goes in the file.
  </Step>
  <Step title="Turn on TLS and the API key">
    In `routr.yaml`, give `spec.data` the key and the certificate, and give the EdgePort its keystore and TLS transports. The snippet shows only what changes.

    ```yaml
    spec:
      edgeport:
        transport:
          - protocol: udp
            port: 5060
          - protocol: tls
            port: 5061
          - protocol: wss
            port: 5063
        securityContext:
          keyStore: /etc/routr/certs/signaling.p12
          keyStorePassword: secret://env/PKCS12_PASSWORD
          keyStoreType: pkcs12
          client:
            authType: DisabledAll
      data:
        apiKeys:
          - secret://env/ROUTR_API_KEY
        tls:
          certFile: /etc/routr/certs/server.crt
          keyFile: /etc/routr/certs/server.key
    ```

    Without `apiKeys` (or a client CA, below), the Data API refuses to start on any address but loopback. `tls` alone encrypts the connection but lets anyone in. See [server keys](/reference/configuration#server-keys).
  </Step>
  <Step title="Mount the certificates and pass the secrets">
    Mount the files individually into `/etc/routr/certs`, pass the two secrets, and publish the TLS ports.

    ```yaml compose.yaml
    services:
      routr:
        image: fonoster/routr-one
        environment:
          PKCS12_PASSWORD: ${PKCS12_PASSWORD}
          ROUTR_API_KEY: ${ROUTR_API_KEY}
        ports:
          - 5060:5060/udp
          - 5061:5061
          - 5063:5063
          - 51907:51907
        volumes:
          - ./routr.yaml:/etc/routr/routr.yaml
          - ./server.crt:/etc/routr/certs/server.crt
          - ./server.key:/etc/routr/certs/server.key
          - ./ca.crt:/etc/routr/certs/ca.crt
    ```

    Mount files, not the whole directory. The container writes `signaling.p12` into `/etc/routr/certs` and needs that directory to stay writable. Leave out the `ca.crt` line if your CA bundle is already in `server.crt`.
  </Step>
  <Step title="Restart the server">
    Recreate the container so it rebuilds the keystore and reads the file.

    ```bash
    PKCS12_PASSWORD=use-a-strong-password ROUTR_API_KEY=<your key> docker compose up -d
    ```
  </Step>
  <Step title="Verify SIP over TLS">
    Open a TLS connection to the signaling port. Replace the address with your server's.

    ```bash
    openssl s_client -connect 192.168.1.3:5061
    ```

    <Check>The output shows your certificate chain and a completed handshake.</Check>
  </Step>
  <Step title="Connect rctl with the key">
    `rctl` reads the key from `ROUTR_API_KEY`, which keeps it out of your shell history. With a self-signed certificate, pass your CA with `--cacert`; with a certificate from a trusted CA, no flag is needed. The host in `--endpoint` must match the certificate's `CN`.

    ```bash
    export ROUTR_API_KEY=<your key>
    rctl domains get --endpoint localhost:51907 --cacert ./ca.crt
    ```

    <Check>The command lists your Domains. Without the key it fails with `authentication required`.</Check>

    The SDK takes the same settings through the `apiKey` and `cacert` options. See [Manage resources with the Node.js SDK](/guides/manage-resources-with-the-sdk).
  </Step>
</Steps>

## Rotate the API key

`apiKeys` is a list, and any key in it is accepted. To rotate without downtime, add the new key next to the old one, restart, move every client to the new key, then remove the old one and restart again.

```yaml
spec:
  data:
    apiKeys:
      - secret://env/ROUTR_API_KEY
      - secret://env/ROUTR_API_KEY_NEXT
```

## Require client certificates (optional)

To authenticate callers by certificate instead of, or next to, the API key, add `tls.clientCAFile`. A caller whose certificate your CA signed is let in; a certificate it didn't sign fails the handshake. Callers with a valid API key and no certificate are still let in.

```yaml
spec:
  data:
    tls:
      certFile: /etc/routr/certs/server.crt
      keyFile: /etc/routr/certs/server.key
      clientCAFile: /etc/routr/certs/ca.crt
```

A component that dials the Data API presents its certificate with `tls.certFile` and `tls.keyFile` in its [client keys](/reference/configuration#client-keys).

## The other gRPC services

RoutrOne also serves the Location (`51902`), Connect (`51904`) and the Dispatcher (`51901`) over gRPC, for components outside it. They take the same `apiKeys`, `tls` and `insecure` keys in their sections, but start without them and log `this gRPC service authenticates nobody`. If nothing outside RoutrOne calls them, turn them off with `bindAddr: ""`, or don't publish their ports.

The Requester (`51909`), which runs with `spec.registry`, has the same rule as the Data API: it refuses to start beyond loopback without authentication. When nothing outside RoutrOne calls it, set `spec.requester.bindAddr: ""`.

## Configure a softphone for TLS

Point the softphone's outbound proxy at port `5061` with `transport=tls`. The exact field name depends on the softphone. In Blink Pro, open the account, choose **Advanced** > **SIP Signaling**, and set **Primary Proxy** to `<host>:5061;transport=tls`.

## Choose TLS versions and cipher suites

The EdgePort uses TLS 1.3 only, on both the TLS and WSS transports. That applies to connections from phones and to the connections the EdgePort opens to carriers and peers. If a phone or carrier doesn't support TLS 1.3, enable TLS 1.2 as well:

- **routr.yaml:** set `spec.edgeport.securityContext.client.protocols` to `[TLSv1.3, TLSv1.2]`.
- **`edgeport.yaml`:** set `spec.securityContext.client.protocols`.
- **Helm:** set `edgeport.tls.protocols` to `[TLSv1.3, TLSv1.2]`.

TLS 1.2 then uses ECDHE suites with AES-GCM or ChaCha20 only. To change the cipher suites, set `client.cipherSuites` or `edgeport.tls.cipherSuites`. TLS 1.3 suites can't be changed. See [`spec.edgeport`](/reference/configuration#spec-edgeport) for the defaults.

To check what the EdgePort accepts, run `openssl s_client -connect <host>:5061 -tls1_3`. A working connection prints `New, TLSv1.3`.

## Call a carrier over TLS

A trunk whose outbound URI has `transport: tls` makes the EdgePort open a TLS connection to the carrier for every call that leaves through it. Three things must be true:

1. The EdgePort has a `tls` transport and a `securityContext` with a keystore, as set up above. The connection to the carrier leaves from that listening point. Without it the call fails and Connect logs `no listening point found for transport TLS`.
2. The EdgePort accepts the carrier's certificate. With `client.authType: DisabledAll`, the EdgePort skips certificate validation on the connections it opens, so any carrier certificate is accepted. With any other `authType`, the carrier's certificate is checked against the system's CAs plus your `trustStore`. Leave `trustStore` unset when the carrier uses a public CA, or point it at a PKCS#12 or PEM file that holds the carrier's private CA.
3. The TLS versions overlap. Most carriers negotiate TLS 1.2, so enable it as shown in [Choose TLS versions and cipher suites](#choose-tls-versions-and-cipher-suites).

Carriers that require TLS usually require SRTP as well. SRTP follows the transport: when RTPEngine is in the path, the media relay asks it for SDES-SRTP (`RTP/SAVP` with `a=crypto` lines) on every leg that uses TLS, and plain RTP or DTLS-SRTP on the other leg as before. There is nothing to configure on the trunk. Without RTPEngine (no `spec.rtprelay` in routr.yaml, or no RTPRelay middleware in a split deployment) the carrier receives the caller's SDP unchanged and will reject plain RTP.

If the carrier accepts only some SRTP crypto suites, override the `SDES` key of the `phone-to-secure-phone` and `web-to-secure-phone` profiles:

```yaml
spec:
  rtprelay:
    host: rtpengine
    port: 22222
    profiles:
      phone-to-secure-phone:
        SDES:
          - only-AES_CM_128_HMAC_SHA1_80
```

In a split deployment the same map goes under `spec.profiles` of `rtprelay.yaml`; on Kubernetes, in the `rtprelay.profiles` Helm value. See [RTPRelay](/reference/components/rtprelay).

To present your Number as the caller identity a carrier checks, see [Caller identity](/reference/resources/trunks#caller-identity).

## Encrypt credentials at rest

With the PostgreSQL backend, the Data API stores Credentials passwords in plain text unless `spec.data.encryptionKey` is set. With a key, it encrypts the password field with AES-GCM before writing it and decrypts it on read, in the same format as Routr 2.

Generate a key:

```bash
npx @47ng/cloak generate
```

Keep the key outside the file, and reference it:

```yaml
spec:
  data:
    encryptionKey: secret://env/CLOAK_ENCRYPTION_KEY   # k1.aesgcm256....
```

On Kubernetes, set `apiserver.cloakEncryptionKey`. Keep the key with your database backups: without it, the stored passwords can't be read. If the database holds encrypted passwords and the key is missing, the Data API refuses to start.

## Other deployments

- **Split Docker deployment.** The `fonoster/routr-edgeport` image builds `signaling.p12` from `/etc/routr/certs/server.crt` and `server.key` at startup, the same way routr-one does. Point `spec.securityContext` in `edgeport.yaml` at the keystore. `fonoster/routr-pgdata` doesn't generate certificates: mount them and name them in `spec.data.tls` of its `data.yaml`. Every component that calls the Data API or the Requester needs the key in its client keys, such as `apiAuth` in `connect.yaml`. See [Standalone component files](/reference/configuration-files).
- **Kubernetes.** The chart generates an API key into `<release>-routr-api-key` and, with `apiserver.tlsOn` (the default), a CA and certificate for the Data API. Set `apiserver.apiKey` and `apiserver.tlsSecret` to use your own. `edgeport.transport.tls.enabled` turns on SIP over TLS; change `edgeport.pkcs12Password` from its default. See [Helm values](/reference/helm-values).

## Troubleshooting

- **The container exits with `refusing to serve the Data API`.** `spec.data` has no `apiKeys`, no `tls.clientCAFile` and no `insecure: true`, and `bindAddr` isn't loopback. Add a key.
- **`rctl` fails with `authentication required`.** `ROUTR_API_KEY` is unset or isn't one of `apiKeys`.
- **`rctl` reports a certificate error.** The endpoint host doesn't match the certificate's `CN`, or you used a self-signed certificate without `--cacert`. If the Data API has no `tls`, pass `--insecure`.
- **A phone or a TLS trunk fails the TLS handshake.** It probably doesn't support TLS 1.3. Enable TLS 1.2 as shown in [Choose TLS versions and cipher suites](#choose-tls-versions-and-cipher-suites).
- **A call to a TLS trunk fails the handshake with a certificate error.** `authType` isn't `DisabledAll` and the EdgePort doesn't trust the carrier's certificate. Add the carrier's CA to `trustStore`.
- **Browsers refuse the WSS connection.** Use a certificate from a trusted CA. See [Enable WebRTC clients](/guides/enable-webrtc).
- **The EdgePort fails to load the keystore.** `keyStorePassword` must be the `PKCS12_PASSWORD` the keystore was built with. Recreate the container after changing it.
