Install Routr Connect on a Kubernetes cluster with the `routr/routr-connect` chart. The chart runs each component as its own workload, writes each component's configuration file from your values, and installs PostgreSQL and Redis as dependencies.

This guide covers chart 0.5 and later, which runs Routr 3. To upgrade a release of chart 0.4.x (Routr 2), see [Upgrade from Routr 2](/guides/upgrade-to-routr-3#upgrade-the-helm-chart).

## Prerequisites

- A Kubernetes cluster (v1.25.4 or later) with a persistent volume provisioner. Minikube or Docker Desktop work for local testing.
- Helm v3.11.1 or later and `kubectl`.
- The address SIP clients use to reach the cluster: a node IP, a load balancer IP, or a DNS name.

## Install the chart

<Steps>
  <Step title="Add the Helm repository">
    Add the Routr chart repository and refresh your local cache.

    ```bash
    helm repo add routr https://routr.io/charts
    helm repo update
    ```

  </Step>
  <Step title="Create a namespace">
    Use a dedicated namespace to keep upgrades and cleanup simple.

    ```bash
    kubectl create namespace sipnet
    ```

  </Step>
  <Step title="Write a values file">
    Create a `values.yaml` file. At minimum, set `edgeport.externalAddrs` so the EdgePort advertises an address clients can reach.

    ```yaml
    edgeport:
      # Address SIP clients use to reach the EdgePort
      externalAddrs: [192.168.1.3]
    ```

    See [Choose key values](#choose-key-values) for the settings you are most likely to change.

  </Step>
  <Step title="Install the release">
    Install the chart with the release name `sipnet`.

    ```bash
    helm install sipnet routr/routr-connect --namespace sipnet -f values.yaml
    ```

    Helm prints `STATUS: deployed` when it has created the release.

  </Step>
  <Step title="Wait for the pods">
    List the pods and wait until they are all running. The first start takes a few minutes while PostgreSQL initializes and migrations run.

    ```bash
    kubectl get pods -n sipnet
    ```

    <Check>When every pod shows `Running`, the release is ready. The migrations pod runs as a post-install hook and is removed when it succeeds.</Check>

  </Step>
  <Step title="Reach the Data API">
    The Data API isn't exposed outside the cluster. It requires an API key and, with `apiserver.tlsOn` (the default), serves TLS. The chart generates both once and keeps them in Secrets of the release. Read the key and the CA, then forward the Service's port `51907`, where `rctl` looks by default, to your machine.

    ```bash
    export ROUTR_API_KEY=$(kubectl get secret -n sipnet sipnet-routr-api-key -o jsonpath="{.data.apiKey}" | base64 -d)
    kubectl get secret -n sipnet sipnet-routr-apiserver-tls -o jsonpath="{.data.ca\.crt}" | base64 -d > ca.crt
    kubectl -n sipnet port-forward svc/sipnet-routr-apiserver 51907
    ```

    In another terminal with the same `ROUTR_API_KEY`, create a Domain with [rctl](/guides/manage-resources-with-rctl).

    ```bash
    rctl domains create --cacert ca.crt
    ```

  </Step>
</Steps>

## Choose key values

Pass values with `-f values.yaml` or `--set key=value`. These are the ones most deployments touch. For every parameter and its default, see [Helm values](/reference/helm-values).

The following example exposes UDP and TCP through cloud load balancers and uses an external database. Run the migrations against it first if it is new; the chart's migrations hook does that when `apiserver.migrations.enabled` is `true`, the default.

```yaml
edgeport:
  externalAddrs: [sip.example.com]
  serviceTypeUDP: LoadBalancer
  serviceTypeTCP: LoadBalancer
  transport:
    tcp:
      enabled: true

apiserver:
  databaseUrl: postgresql://routr:secret@dbserver:5432/routr?schema=public

postgresql:
  enabled: false
```

<Note>
Every EdgePort replica can receive any request. When a request lands on an EdgePort that doesn't hold the callee's connection, Routr forwards it to the EdgePort that does. See [EdgePort cooperation](/concepts/edgeport-cooperation).
</Note>

## Scale the release

The chart scales the two kinds of component differently.

- **EdgePorts, one per node.** A required pod anti-affinity never puts two EdgePorts on one node, so `edgeport.replicas` is the number of nodes that take SIP traffic; a replica beyond that stays `Pending`. With `externalTrafficPolicyUDP` or `externalTrafficPolicyTCP` set to `Local`, the load balancer sends each node its share and keeps the caller's address, and nodes without an EdgePort fail its health check and get no traffic.
- **Stateless services, as replicas.** Connect, the Data API, Location and the Dispatcher (when on) run 2 replicas by default, spread over the nodes, each with a PodDisruptionBudget that keeps one running through a node drain. Their callers dial headless Services (`<release>-routr-<service>-headless`) and balance gRPC calls round robin over every ready pod, so a replica you add takes its share. Location replicas share registrations through Redis.

Raise `<service>.replicas` and `<service>.resources.requests` with your traffic. As a reference, at 325 calls/s on DigitalOcean Connect used about 2 cores, the Data API 1.1 and Location 0.3. A new replica gets calls once its callers re-resolve the name, which they do when a connection breaks or a pod goes away, not the moment it starts.

## Trunk registration

The Registry sends a Trunk's REGISTER through the Requester, with the Trunk's credentials in `X-Gateway-Auth`. Connect honors that header only from `connect.trustedRegistryAddresses`. The default is the DNS name of the Requester's headless Service, `<release>-routr-requester-headless.<namespace>`, which resolves to exactly the Requester's pods.

Connect resolves the name every 10 seconds, so a new Requester pod is trusted within that time; its first REGISTER may be challenged, and the next round goes through. If the name stops resolving, Connect keeps its last addresses for 30 seconds and then trusts nothing, logging `X-Gateway-Auth from an address not in trustedRegistryAddresses` for each REGISTER it refuses.

The list also takes IPs, CIDRs and other names, for a Requester outside the release. An empty list fails the install while `registry.enabled` is `true`. Don't use a CIDR that covers the pod network: with `externalTrafficPolicy: Cluster`, a node can rewrite an outside caller's address into it.

## Expose EdgePort through a cloud load balancer

On a managed cluster, a `LoadBalancer` Service gives the EdgePort a public IP. You only learn that IP after the load balancer exists, so set it in two passes.

<Steps>
  <Step title="Request a load balancer">
    Set the UDP Service type, leaving `externalAddrs` unset for now.

    ```bash
    helm upgrade --install sipnet routr/routr-connect --namespace sipnet \
      -f values.yaml --set edgeport.serviceTypeUDP=LoadBalancer
    ```

  </Step>
  <Step title="Wait for the external IP">
    The cloud provider creates the load balancer for the `sipnet-routr-edgeport-udp` Service. Wait until `EXTERNAL-IP` shows an address instead of `<pending>`.

    ```bash
    kubectl get svc -n sipnet sipnet-routr-edgeport-udp --watch
    ```

  </Step>
  <Step title="Advertise the address">
    Set `edgeport.externalAddrs` to that IP, keeping the values already in the release.

    ```bash
    helm upgrade sipnet routr/routr-connect --namespace sipnet \
      --reuse-values --set "edgeport.externalAddrs={203.0.113.10}"
    ```

    Add the IP to `values.yaml` too, so later upgrades with `-f values.yaml` keep it.

  </Step>
</Steps>

<Warning>
The chart only sets the Service type. Your provider must support UDP load balancers, and its firewall rules must allow UDP `5060`, or the node port when you keep `NodePort`. Without UDP load balancing, keep `NodePort` and point clients at a node's public IP and the assigned node port.
</Warning>

For TCP, TLS, WS, and WSS, set `edgeport.serviceTypeTCP` the same way. It creates the `sipnet-routr-edgeport-tcp` Service.

## Upgrade the release

Refresh the repository and apply the new chart version with the same values file. The chart runs the migrations image, `fonoster/routr-pgdata-migrations` at its `appVersion`, in a post-upgrade hook; it applies Routr 2's migrations unchanged, and Routr 3 keeps that schema.

```bash
helm repo update
helm upgrade sipnet routr/routr-connect --namespace sipnet -f values.yaml
```

Check the [changelog](/changelog) before upgrading across major versions. When an EdgePort pod restarts, the clients connected to it register again, and requests inside calls it carried, BYE included, are answered `481`.

### Scale-out defaults

Connect, the Data API and Location now run 2 replicas each, with CPU and memory requests, and the EdgePorts at most one per node. Before you upgrade, check that the cluster has room for the requests, set `edgeport.replicas` to no more than the nodes that can run EdgePorts (`1` on a single-node cluster), and set `location.replicas: 1` if Location uses the `memory` cache. The HorizontalPodAutoscalers are now off unless `<service>.autoscaling.enabled` is `true`.

### From chart 0.4.x (Routr 2)

Chart 0.5 runs Routr 3 on the same database, with no data migration, but several values changed and the Data API now requires an API key. Follow [Upgrade from Routr 2](/guides/upgrade-to-routr-3#upgrade-the-helm-chart) before you run `helm upgrade`.

### From chart 0.4.7 or earlier

The EdgePort StatefulSet now uses the `<release>-routr-edgeport-headless` Service as its governing Service. Kubernetes doesn't allow changing that field on an existing StatefulSet, so delete the StatefulSet first, leaving its pods running, and then upgrade:

```bash
kubectl delete statefulset sipnet-routr-edgeport --cascade=orphan --namespace sipnet
helm upgrade sipnet routr/routr-connect --namespace sipnet -f values.yaml
```

The pods keep serving traffic until the upgraded StatefulSet replaces them.

## Uninstall the release

Remove the release and its Kubernetes objects.

```bash
helm uninstall sipnet --namespace sipnet
```

Helm keeps the persistent volume claims, so your database survives. To delete them as well, remove the PVCs for the release.

```bash
kubectl delete pvc -l app.kubernetes.io/instance=sipnet -n sipnet
```

<Warning>Deleting the PVCs deletes the PostgreSQL data. Back it up first.</Warning>

## Troubleshooting

- **Clients register but calls have no audio or replies are lost.** `edgeport.externalAddrs` doesn't match the address clients use.
- **No external IP for SIP.** With the default `NodePort` service type, clients must use a node IP and the assigned node port. Use `LoadBalancer` on cloud providers. See [Expose EdgePort through a cloud load balancer](#expose-edgeport-through-a-cloud-load-balancer).
- **`rctl` can't connect.** Check that the port-forward is still running and that you match the TLS mode: `--cacert ca.crt` when `apiserver.tlsOn` is `true`, `--insecure` when it is `false`.
- **`rctl` reports `authentication required`.** `ROUTR_API_KEY` isn't the key in `<release>-routr-api-key`, or in `apiserver.apiKeySecret`.
- **Trunks don't register.** Connect logs `X-Gateway-Auth from an address not in trustedRegistryAddresses`. See [Trunk registration](#trunk-registration).
- **`helm install` fails on `global.logsLevel`.** Routr 2's `verbose` and `silly` are gone: use `debug`.
