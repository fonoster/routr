title: "Scale the Location Service with Redis"
sidebarTitle: "Scale with Redis"
description: "For operators growing past one Location Service instance: switch the registration cache from memory to Redis with routr-one, a split Docker deployment, or Kubernetes."
---

Store registrations in Redis instead of process memory, so several Location Service instances share one view of where every endpoint is.

## When you need Redis

The Location Service supports two cache providers: `memory` and `redis`. Memory is fine for a single instance. Switch to Redis when any of these apply:

- **You run more than one Location Service instance.** With `memory`, each instance only knows the registrations it received, so lookups on another instance miss them.
- **You balance Peers with `least-sessions` across several instances.** The algorithm picks the Peer contact with the lowest session count reported in its last REGISTER. It works with either provider, but every instance must see the same registrations. See [Load balancing](/concepts/load-balancing).
- **You want registrations to survive a Location Service restart.** With `memory`, a restart clears the location table until clients register again.

## Prerequisites

- A Redis server reachable from the Location Service, or permission to run one next to it.

## Switch the cache provider

<Tabs>
  <Tab title="Docker (routr-one)">
    <Steps>
      <Step title="Add Redis to your Compose file">
        Add a Redis service next to `routr` in the `compose.yaml` from [Deploy with Docker](/guides/deploy-with-docker).

        ```yaml
        services:
          redis:
            image: redis:7.4.7-alpine
            expose:
              - 6379
        ```
      </Step>
      <Step title="Point the Location at Redis">
        Set [`spec.location.cache`](/reference/configuration#spec-location) in `routr.yaml`.

        ```yaml routr.yaml
        apiVersion: v3
        kind: Routr
        ref: routr-one
        spec:
          edgeport:
            externalAddrs:
              - "${DOCKER_HOST_ADDRESS}"
            transport:
              - protocol: udp
                port: 5060
          location:
            cache:
              provider: redis
              parameters: host=redis,port=6379
          data:
            backend: postgres
            url: secret://env/DATABASE_URL
            apiKeys:
              - secret://env/ROUTR_API_KEY
        ```

        `parameters` takes comma-separated `key=value` pairs and defaults to `host=localhost,port=6379`. The accepted keys are `host`, `port`, `username`, `password`, and `secure` (set `secure=true` to connect over TLS). Any other key stops Routr at startup.
      </Step>
      <Step title="Restart the services">
        ```bash
        DOCKER_HOST_ADDRESS=192.168.1.3 docker compose up -d redis routr
        ```
      </Step>
    </Steps>

  </Tab>
  <Tab title="Docker (split)">
    <Steps>
      <Step title="Add Redis to your Compose file">
        Add a Redis service next to the `location` service. The following snippet shows only the services that change.

        ```yaml
        services:
          location:
            image: fonoster/routr-location
            expose:
              - 51902
            volumes:
              - ./config/location.yaml:/etc/routr/location.yaml

          redis:
            image: redis:7.4.7-alpine
            expose:
              - 6379
        ```
      </Step>
      <Step title="Point the Location Service at Redis">
        Set `cache.provider` to `redis` and pass the connection in `cache.parameters` as comma-separated `key=value` pairs.

        ```yaml location.yaml
        kind: Location
        apiVersion: v2beta1
        metadata:
          region: default
        spec:
          bindAddr: 0.0.0.0:51902
          cache:
            provider: redis
            parameters: host=redis,port=6379
        ```

        The accepted keys are `host`, `port`, `username`, `password`, and `secure` (set `secure=true` to connect over TLS). Always set `host` and `port`. Any other key makes the service fail to start.
      </Step>
      <Step title="Restart the services">
        Recreate the Location Service so it loads the new configuration.

        ```bash
        docker compose up -d redis location
        ```
      </Step>
    </Steps>

  </Tab>
  <Tab title="Kubernetes (Helm)">
    The `routr-connect` chart uses Redis by default: `location.cache.provider` is `redis` and `redis.enabled` installs a standalone Redis next to the release. If you changed either value, restore them in `values.yaml`.

    ```yaml
    location:
      cache:
        provider: redis

    redis:
      enabled: true
    ```

    To use your own Redis server instead, turn off the bundled one and pass the connection parameters.

    ```yaml
    location:
      cache:
        provider: redis
        parameters: host=redis.example.internal,port=6379,password=secret

    edgeport:
      cache:
        parameters: host=redis.example.internal,port=6379,password=secret

    redis:
      enabled: false
    ```

    Apply the change to your release.

    ```bash
    helm upgrade sipnet routr/routr-connect --namespace sipnet -f values.yaml
    ```

    The Registry service has its own `registry.cache.provider` and `registry.cache.parameters` values, which also default to Redis. The EdgePorts use Redis too when the release has one (`edgeport.cache.provider`, `edgeport.cache.parameters`): they keep the dialogs of the calls in progress there so a restarted pod can still take their BYE. See [Helm values](/reference/helm-values).

  </Tab>
</Tabs>

## Verify

Check the logs for the provider that was loaded.

```bash
docker compose logs location
```

<Check>The standalone Location logs `msg="routr location"` with `cache=redis`. With Redis reachable at startup, it also logs `indexed the bindings in redis`, and so does routr-one (`docker compose logs routr`). On Kubernetes, run `kubectl logs` on a Location pod instead.</Check>

Register a softphone, then list the keys in Redis. Routr 3 keeps the key names Routr 2 wrote, so a rollout can mix versions, and adds an index of its own, so a lookup never scans the keyspace.

```bash
docker compose exec redis redis-cli --scan
```

## Pitfalls

- **Redis unreachable at startup.** The Location starts anyway and logs `unable to index the bindings in redis at startup`. Its lookups fail until Redis is back. Check that `host` and `port` resolve from inside the Location Service or routr-one container.
- **Two live contacts for one address of record.** With Redis, the contact is picked by binding key; with `memory`, the newest wins. Don't rely on either order.
- **Registrations disappear.** Each entry expires with the registration's `expires` value. Clients must refresh their registration before it expires.
- **Old registrations after switching.** Registrations held in memory are not migrated. Clients appear in Redis after their next REGISTER.
